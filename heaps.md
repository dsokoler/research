# Windows User-Mode Heap Overflow Exploitation: NT Heap/LFH vs. Segment Heap on Windows 11 (24H2/25H2)

## TL;DR

- **Two allocators coexist on modern Windows 11:** traditional Win32 desktop processes still default to the **NT Heap** (RtlHeap) with the **Low Fragmentation Heap (LFH)** front end, while UWP/MSIX "Windows apps," a fixed set of system binaries (csrss, lsass, runtimebroker, services, smss, svchost), and manifest/IFEO opt-in processes use the **Segment Heap** (signature `0xDDEEDDEE`, gated by bit 0 of `ntdll!RtlpHpHeapFeatures`). Which allocator a target uses decides your entire grooming strategy, so step one of any heap exploit is fingerprinting `_HEAP` vs `_SEGMENT_HEAP`.
- **Inline metadata corruption is *conditionally* dead; adjacency-driven data corruption is the default state of the art.** XOR-encoded `_HEAP_ENTRY` headers, safe unlinking, RB-tree/linked-list fast-fail checks, encoded VS sizes/LFH block offsets, LFH allocation-order randomization and guard pages have pushed practical exploitation away from "overwrite the free-list pointer" toward precise heap grooming that places a corruptible **application object** (length field, type tag, pointer, vtable) adjacent to the overflow. On the Segment Heap the LFH has *no* inline per-block header at all, so an overflow lands directly in neighboring object data. **The crucial caveat (§2.5): metadata corruption is not categorically dead — it is gated on the secrecy of the per-heap `Encoding` and the global LFH/heap keys. An info leak that recovers those keys reopens forged-header and forged-offset primitives.**
- **For defenders, high-fidelity runtime detection of the overflow itself is hard; the strongest signals are the mitigation-triggered terminations and the post-exploitation memory operations.** `__fastfail`/`RtlFailFast` (exception `0xC0000409`), `STATUS_HEAP_CORRUPTION` (`0xC0000374`) surfaced through WER/Watson, CFG/CET fail-fast buckets, and ETW Threat-Intelligence (`Microsoft-Windows-Threat-Intelligence`) telemetry on `NtAllocateVirtualMemory`/`NtProtectVirtualMemory` RX/RWX transitions are the practical EDR signals. Data-only corruption that never crashes, and grooming that looks like ordinary allocation traffic, remain the hard blind spots.

## 1. NT Heap vs. Segment Heap: which process uses which, and why it matters

### Allocator selection in modern Windows

The NT Heap is the legacy user-mode implementation (`ntdll!_HEAP`, segment signature `0xFFEEFFEE`) that has backed every Win32 process since before Windows 10. The Segment Heap (`ntdll!_SEGMENT_HEAP`, signature `0xDDEEDDEE`) was introduced in Windows 10 and is the modern native heap. Both are still present on Windows 11 24H2/25H2; the Segment Heap did **not** replace the NT Heap.

Selection logic (resolved in `RtlInitializeHeapManager` → `RtlpHpOptIntoSegmentHeap` during process init; Yason, BH USA 2016):

- **Opted-in by default:** UWP/"Windows app" (formerly Modern/Metro, now MSIX-packaged) processes, and executables whose image name matches a hardcoded list of system binaries — `csrss.exe`, `lsass.exe`, `runtimebroker.exe`, `services.exe`, `smss.exe`, `svchost.exe`. If a process is opted in, bit 0 of the global `RtlpHpHeapFeatures` is set.
- **Per-image opt-in/out (IFEO):** `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Image File Execution Options\<exe>\FrontEndHeapDebugOptions` — bit 2 (`0x04`) disables, bit 3 (`0x08`) enables the Segment Heap for that image name.
- **Machine-wide:** `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Segment Heap\Enabled` (0 disables, non-zero enables).
- **Per-heap:** even in a Segment-Heap-enabled process not every heap is a Segment Heap. `HeapCreate()` produces a Segment Heap only if the heap is growable (`dwMaximumSize == 0`). `RtlCreateHeap()` requires `HEAP_GROWABLE`, a NULL `HeapBase`, NULL `Lock`, and zeroed `SegmentReserve`/`SegmentCommit`/`VirtualMemoryThreshold`/`CommitRoutine`. Pre-allocated/shared heaps (e.g. `ntdll!CsrPortHeap`) and non-growable heaps stay on the NT Heap. The CRT heap (`msvcrt!crtheap`) in an Edge content process is a Segment Heap.

**The `FrontEndHeapType` field** in `_HEAP` (the field is at a build-dependent offset — commonly cited at `+0x0d6` on older x86 and documented as `+0x1a2` in recent x64 layouts) encodes the front end: `0` = backend only, `1` = legacy lookaside (obsolete), `2` = LFH, `3` = the VS/Segment front end variant. Reading this field is how exploit code and debuggers decide which path an allocation will take.

### Practical implications for exploitation

- **Browsers are the central case and are mixed.** Microsoft Edge (both legacy EdgeHTML and Chromium Edge) runs with the Segment Heap enabled; Chromium experimented with it and disabled it by default over a renderer CPU/perf regression, asking Microsoft for a simple toggle for the `segment-heap-enabled` bit in `RtlpHpHeapFeatures`. On Windows ARM64 the Segment Heap is the platform default. In practice you must assume the component you are attacking in a Windows app uses the Segment Heap unless it ships a custom allocator (V8/Oleaut/jemalloc-style arenas, PartitionAlloc, etc.) — many of the most interesting browser targets bypass the OS heap entirely with their own allocators, which is why so much browser exploitation is really about the engine allocator, not RtlHeap.
- **Tooling caveat on 24H2:** the WinDbg `!heap` extension has known gaps parsing Windows 11 heap structures — it may list only the default process heap and misreport user-created heaps — so expect to walk `_SEGMENT_HEAP`/`_HEAP` by hand with `dx` (see §2.8).

## 2. Offensive techniques & primitives

### 2.1 NT Heap backend internals and the corruption surface

The `_HEAP` structure is the per-heap control block. Fields that matter to an attacker:

- `Encoding` (`_HEAP_ENTRY` at `+0x080`) and `EncodeFlagMask` (`+0x07c`, set to `0x00100000` once encoding is active): the per-heap XOR key and the mask that decides whether chunk headers are encoded. **Leaking `Encoding` is the master key to the backend** (§2.5).
- `BlocksIndex` (`+0x138`): pointer to the `_HEAP_LIST_LOOKUP` structure used to accelerate free-chunk lookup.
- `FreeLists` (`+0x150`): the doubly-linked list head(s) of free backend chunks.
- `FrontEndHeap` (`+0x198`), `FrontEndHeapType` (`+0x1a2`), and `FrontEndHeapStatusBitmap` (`+0x1b2`, 129 bytes): front-end allocator pointer, type, and the per-size-class activation bitmap.
- `VirtualMemoryThreshold` (`0xfe00` 8-byte units ≈ 512KB-ish): requests above this go straight to `VirtualAlloc` and are tracked in `VirtualAllocdBlocks` (`+0x110`).

A `_HEAP_SEGMENT` (signature `0xFFEEFFEE`) describes one contiguous reserved/committed region; a heap can own several, linked via `SegmentList`. Backend chunks carry an 8-byte `_HEAP_ENTRY` header: `Size` (in 8-byte/16-byte granularity units), `Flags` (BUSY, LAST_ENTRY, etc.), `SmallTagIndex`, `PreviousSize`, `SegmentOffset`, `UnusedBytes`. Free backend chunks become `_HEAP_FREE_ENTRY`, adding the `FreeList` `LIST_ENTRY` (Flink/Blink). Allocation flow: `malloc`/`HeapAlloc` → `RtlAllocateHeap` → LFH (`RtlpLowFragHeapAlloc`) if the front end is active for that size, else the backend `RtlpHeapAlloc`, which services from the `ListHint`/`FreeLists`, splitting a larger free chunk or extending the segment if needed. Modern backend free management uses the `BlocksIndex`/`ListHint` with a `FreeListInUse`-style bitmap rather than the old XP `FreeList[]` array.

**Backend corruption primitives.** Even though the LFH services most small allocations, the backend remains the target whenever you can keep the victim size out of the LFH (see §2.4) or force a backend path. The levers:

- **Encoded-header survivability (what a linear overflow may get away with).** The `_HEAP_ENTRY` is XOR-encoded against `_HEAP.Encoding`, and the encoding carries a one-byte checksum (the XOR of the preceding header bytes). The heap manager decodes and validates this on alloc/free/coalesce; a forged or clobbered header fails the check and raises a heap-corruption fast-fail unless `Encoding` is known. The practical consequence for a *small* linear overflow is that whether you survive depends on which header bytes the overflow perturbs and when that header is next decoded — overrunning into the encoded Size/Flags/checksum unit of the adjacent chunk is an (near-)immediate fast-fail at the next operation touching that chunk, whereas not touching the next header at all (overflow confined to the current chunk's own slack/`UnusedBytes` or into the next chunk's *user data*) is survivable. This is exactly why the modern approach steers the overflow into neighbor **object data** rather than neighbor metadata.
- **Coalescing abuse (`RtlpCoalesceFreeBlocks`).** On free, the backend merges the freed chunk with physically adjacent free chunks — forward by computing the next chunk address from `Size`, backward using `PreviousSize` when the previous chunk's BUSY flag is clear. If you can corrupt an adjacent chunk's `Size`/`PreviousSize`/`Flags` (e.g. clear BUSY, or desync `PreviousSize` so the "previous" chunk the allocator walks back to is actually a live object), the coalesce swallows a live allocation into a larger free run; a subsequent allocation of that size is then handed memory **overlapping the live object** — a type-confusion/overlap primitive. Safe unlinking (`E->Flink->Blink == E->Blink->Flink == E`) protects the `FreeList` pointer manipulation that coalescing performs, which is why you drive the merge through *sizes/flags* rather than through forged Flink/Blink.
- **Split / remainder overlap.** When a request is satisfied from a larger free chunk, the backend splits it and returns the remainder to the free list with a freshly written header. Corrupting the size bookkeeping so the computed remainder straddles a still-live object yields the same overlap result from the allocation side rather than the free side. Pairs with the `LAST_ENTRY` flag / segment-extension edge cases, where a corrupted terminal chunk can push the allocator into mis-sizing the next carve.

All of these ultimately converge on the same objective: **an allocation that overlaps a live object**, from which you build relative/arbitrary read-write (§2.4).

### 2.2 LFH internals and the intra-subsegment overflow (NT Heap front end)

The LFH is a "heap inside the heap" that services small, commonly-requested sizes (≤ ~16KB, `0x4000`) from pre-carved `UserBlocks`. Key structures and behaviors:

- Activation heuristic: the LFH turns on for a given size class after **18 consecutive allocations** of a similar size (`0x12`; `0x11` if the bucket was previously active), or via the usage counter crossing its threshold. Once active it stays active for that bucket. Activation is tracked through `FrontEndHeapStatusBitmap`/`FrontEndHeapUsageData`, not the old ListHint.
- `_HEAP_SUBSEGMENT` tracks a bin of same-size chunks; `_HEAP_USERDATA_HEADER` precedes the user chunks; `_INTERLOCK_SEQ` (`Depth`, `FreeEntryOffset`) drives the lock-free allocation cursor.
- The subsegment pointer is itself computed from an encoded header: `SubSegment = *(DWORD*)header ^ (header >> 3) ^ Heap ^ RtlpLFHKey`.
- **LFH allocation randomization** (Windows 8+): `RtlpInitializeLfhRandomDataArray` fills `RtlpLowFragHeapRandomData` with `0x100` random values used to pick the slot for the next allocation, so you cannot assume the Nth allocation lands at the Nth slot.

**The intra-subsegment overflow playbook (the LFH bread-and-butter).** Because every block in a `_HEAP_SUBSEGMENT` belongs to one size class, an overflow inside the LFH is fundamentally an *adjacency within the bucket* game — the NT-heap analogue of the Segment-Heap grooming in §2.4:

1. **Activate** the target bucket (drive ≥18 same-size allocations) so your victim-sized allocations come from a predictable LFH subsegment rather than the backend.
2. **Fill** the subsegment so allocations are dense and contiguous within `UserBlocks`.
3. **Punch a hole** by freeing one block, then **reclaim** it with an attacker-controlled object of the same bucket size, placing attacker data immediately before a chosen victim block.
4. **Overflow** block N into block N+1's **user data** (not its header — LFH blocks still carry a small `_HEAP_ENTRY`, but you aim past/over it into the next object's fields), corrupting a length/type/pointer in the neighbor.

The whole difficulty is step 3's determinism against LFH randomization (§2.4). This same fill→hole→reclaim machinery is what makes **UAF and overflow interchangeable on the LFH**: a UAF frees the victim and you reclaim its exact slot with a confusable object; an overflow corrupts the neighbor you groomed next to it. Everything in the grooming toolbox transfers between the two, and UAF is the more common real-world entry point.

**`_HEAP_USERDATA_HEADER` corruption (a distinct target).** The Win10/11 `_HEAP_USERDATA_HEADER` carries `EncodedOffsets` — a packed `FirstAllocationOffset` + `BlockStride` — encoded against the LFH key and the `UserBlocks` address, plus a `BusyBitmap`. Where a per-chunk overflow corrupts a single neighbor's data, corrupting the subsegment's **stride/first-offset** desynchronizes the allocator's notion of where blocks begin across the whole subsegment, which can be turned into overlapping allocations at a coarser granularity. This requires defeating the offset encoding (again a key-leak dependency, §2.5).

**Status note — `_INTERLOCK_SEQ`/`FreeEntryOffset` is effectively dead on 11.** Valasek's Win7-era technique corrupted `FreeEntryOffset` in `_INTERLOCK_SEQ` to redirect the next LFH allocation. Post-Windows 8 this is impractical: the offsets are encoded and the free-list cursor is updated through an interlocked 64-bit compare-exchange on `AggregateExchg`, so a blind overwrite desyncs rather than redirects and trips corruption checks. Don't chase it on modern Windows — it's of historical interest only.

### 2.3 Segment Heap internals

`_SEGMENT_HEAP` (HeapBase) holds four allocation components plus their state:

- **Backend** (`RtlpHpSegAlloc`): services > 128KB to 508KB at page granularity. Segments are 1MB virtual reservations from `NtAllocateVirtualMemory`. The first `0x2000` bytes of a segment hold the header; the first `_HEAP_PAGE_RANGE_DESCRIPTOR` slot is repurposed to store the `_HEAP_PAGE_SEGMENT` (`ListEntry`, `Signature`, `DescArray[256]`); the second descriptor is unused. Each page gets a `_HEAP_PAGE_RANGE_DESCRIPTOR`; "first" descriptors of free backend blocks are nodes of the **backend free tree** (`FreePageRanges`, an RB tree keyed on page count + encoded commit count). Crucially, backend blocks have **no block header at the start of the user data** — the descriptors live in the segment header, out-of-band.
- **VS (Variable Size)** (`RtlpHpVsContextAllocate…`): services ≤ 128KB. It carves VS subsegments (headed by `_HEAP_VS_SUBSEGMENT`) from the backend and manages free chunks in a best-fit **FreeChunkTree** (RB tree keyed `UnsafeSize<<16 | MemoryCost`). Used chunks carry a `_HEAP_VS_CHUNK_HEADER` whose `Sizes` field (`MemoryCost`, `UnsafeSize`, `UnsafePrevSize`, `Allocated`) is **encoded**: `Sizes.HeaderBits ^ chunk_addr ^ RtlpHpHeapGlobals.HeapKey`. Free chunks use `_HEAP_VS_CHUNK_FREE_HEADER` (RB `Node`).
- **LFH** (`RtlpHpLfhContextAllocate`): per Mark Vincent Yason, "Windows 10 Segment Heap Internals" (Black Hat USA 2016), "The Low Fragmentation Heap (LFH) services allocation requests for <=16,368 bytes but only if the allocation size is [hot]," with LFH buckets 1–64 covering 1–1,024 bytes at 16-byte granularity. Completely re-architected vs. the NT Heap LFH. `LfhContext` (`_HEAP_LFH_CONTEXT`) → buckets (`_HEAP_LFH_BUCKET`) → affinity slots (`_HEAP_LFH_AFFINITY_SLOT`) → `_HEAP_LFH_SUBSEGMENT`. There is **no per-block header**; a 2-bits-per-block **block bitmap** (`BUSY` + `UNUSED BYTES`) in the subsegment tracks state. Per Yason (BH USA 2016), "Bucket activation occurs if there [are] 17 active allocations for the bucket's allocation size. Bucket activation also occurs if there are 2,040 allocation requests for the bucket's allocation size, regardless if [the blocks were previously free]," via `RtlpHpLfhBucketActivate`. The subsegment's block size and first-block offset fields are **encoded** with the LFH key and subsegment address.
- **Large blocks** (`RtlpHpLargeAlloc`): > 508KB, backed directly by virtual memory, metadata in the `LargeAllocMetadata` RB tree, **no header at the start of the block**.

`RtlpHpAllocateHeap` routes by size; if the LFH bucket for a size is not yet active it returns -1 and the request falls through to VS. The **headerless LFH/backend/large-block design is the defining difference from the NT heap**: a linear overflow in those components cannot corrupt inline allocator metadata because there is none at the user block — it necessarily lands in neighboring object data, which is why Segment-Heap exploitation is *inherently* adjacency-grooming-driven, and why the VS allocator (the one component that *does* keep an inline, albeit encoded, header) is the prime metadata target (§2.4).

### 2.4 From overflow to primitive: the modern grooming playbook

Because inline metadata is now encoded/validated (§3), the dominant techniques convert a linear heap overflow into **controlled adjacency** against application data rather than allocator metadata. The toolbox:

- **Grooming / feng shui / massaging.** Sotirov's 2007 "Heap Feng Shui in JavaScript" (HeapLib) established the model: the allocator is deterministic given a known allocation history, so precise allocate/free sequences defragment the heap and place a victim object immediately after an attacker-controlled chunk. Daniel Soeder/Ben Hawkes-era "engineering heap overflow exploits with JavaScript" showed ~1000 allocations drive IE's heap to a predictable, adjacency-reliable state. The same logic is applied today through scripting engines (JS typed arrays/ArrayBuffers, DOM strings) and file-format parsers.
- **Bucket steering (getting attacker and victim into the *same* bin).** Reliable adjacency requires that the attacker chunk and the victim object round to the **same LFH bucket / backend size class**. LFH buckets quantize requested size (roughly 8-byte granularity up to 256 bytes, 16-byte above that, coarsening further toward 16KB), so you pick an attacker object whose size lands in the victim's bucket, and you keep both out of the backend if you want LFH adjacency (or deliberately below/above the LFH range when you want the backend's coalescing/split behavior instead). Misjudging the rounding puts your spray in a neighboring bin and the overflow lands on unrelated allocations.
- **The OleAut32 BSTR cache (a critical process-level gotcha).** Any target that allocates strings via `SysAllocString`/`SysFreeString` (the MSHTML/IE/Office/COM lineage) does **not** return freed BSTRs straight to RtlHeap — OleAut32 keeps a per-size **free-list cache**, so your carefully timed frees never reach the heap and your holes never open. Setting the environment variable `OANOCACHE=1` disables the cache and restores the "free == heap free" assumption grooming depends on. Overlooking this silently destroys adjacency and is one of the most common reasons an otherwise-correct IE-era groom "doesn't work."
- **Deterministic vs. probabilistic adjacency under LFH randomization.** The `0x100`-entry random index (`RtlpLowFragHeapRandomData`) means you cannot assume slot order. Two responses: (a) **spray wide and play the odds** — fill enough of the subsegment that *some* attacker block is adjacent to the victim with high probability, then use an info leak to confirm; or (b) exploit the **activation window** — per Saar Amar's "Deterministic LFH," the behavior around a *freshly activated* bucket / newly created subsegment is the most predictable moment before randomization spreads allocations out, so you time victim placement into that window. Determinism is a function of controlling *when* the bucket activates and how full the subsegment is, not of predicting the RNG.
- **Defeating the LFH deliberately.** A standard move (Rapid7's "Heap Overflow Exploitation on Windows 10," Corelan) is to *avoid* activating the LFH for the victim size (fewer than ~18 same-size allocations) so requests come from the more deterministic backend, then use the backend split/coalesce behavior (§2.1) for controlled adjacency.
- **VS metadata attack (Segment Heap).** Blue Frost Security's "Attacking the VS Allocator" (2022) is the canonical modern Segment-Heap metadata technique: overflow the encoded `_HEAP_VS_CHUNK_HEADER.Sizes.UnsafeSize` of the next ("Bruce Banner") chunk so the allocator perceives it as much larger ("mutant" chunk), free/realloc it, and obtain an **overlapping chunk** that covers a neighboring object — a type-confusion/overlap primitive. Per Blue Frost Security (@_vepe, Aug 16 2022), the minimum required overflow size is 3 bytes, and in the LSB technique "to overwrite the first 16 bytes of the overwritten chunk user data, we have 249/256, 97% success rate (ie any size >=0x70)"; the LSB technique constrains the mutant size within attacker-controlled chunks, while the MSB technique deliberately over-extends and uses "fence" and "trap" chunks injected into the FreeChunkTree to win the race and bury the oversized remainder. The `Allocated` field being treated as "non-zero = allocated" (255/256 odds) is what keeps coalescing from immediately crashing.
- **Converting to R/W and control flow.** Overlap/type-confusion yields a corrupted length/size field → relative read/write; a corrupted pointer → arbitrary read/write; a corrupted vtable or function pointer → control-flow hijack (now gated by CFG/XFG/CET, §3). The 2024 Suraj Malhotra LFH write-up is a representative current chain: activate LFH, fill `UserBlocks`, punch a hole, reclaim with a crafted object, abuse an unchanged size field to overflow, then build arbitrary read/write. Yason's CVE-2016-0117 WinRT PDF case study remains the canonical Segment-Heap end-to-end: groom the MSVCRT Segment Heap via Chakra ArrayBuffers, activate the right LFH bucket, prevent coalescing/guard-page faults, and land a reliable arbitrary write.

### 2.5 The metadata-encoding key angle: when metadata attacks come back

The blanket claim that "heap metadata corruption is dead" is imprecise. What is dead is *blind* metadata corruption. Every modern metadata protection on both allocators is a **secrecy-of-key** scheme, not a structural impossibility:

- **NT backend:** `_HEAP.Encoding` XOR-masks the `_HEAP_ENTRY` and a checksum validates it. Recover `Encoding` (via an info leak of a known chunk header you can also predict the plaintext of, or a direct read of the `_HEAP` structure) and you can forge a valid encoded header for a chosen `Size`/`Flags`, re-enabling classic coalesce/split corruption and even arbitrary-free-style primitives.
- **NT LFH:** the subsegment pointer encoding and `_HEAP_USERDATA_HEADER.EncodedOffsets` are keyed by the global `RtlpLFHKey` (and the structure address). Leak `RtlpLFHKey` and you can forge subsegment offsets / stride.
- **Segment Heap VS:** `_HEAP_VS_CHUNK_HEADER.Sizes` is encoded with `RtlpHpHeapGlobals.HeapKey` XOR the chunk address. With `HeapKey` leaked, the VS overlap attack (§2.4) collapses from a probabilistic size-smear into a *precise* forged-size write. The global encode keys live in a known `ntdll` global, so an arbitrary-read primitive turns the encoded-metadata defenses off wholesale.

So the real decision tree is: **no leak → adjacency/data-only corruption; key leak → forged-metadata corruption is back on the table.** For a defender, this is why protecting the *readability* of `ntdll` heap globals and `_HEAP` control structures (and why info-leak mitigation generally) is load-bearing for the heap-metadata defenses, not just for ASLR.

### 2.6 Target-object catalog and which processes still run the NT heap

The grooming sections tell you *how* to place adjacency; this is *what* to place next to the overflow and *where the NT-heap bugs actually live*.

**High-value victim objects to groom adjacent to the overflow:**

- **Length-prefixed BSTRs** — a `SysAllocString` BSTR stores its byte length in the 4 bytes immediately *before* the character data. Overflow that length field and every subsequent read of the string becomes an out-of-bounds relative read (a clean info-leak primitive); this is the workhorse of MSHTML/scripting-engine exploitation.
- **Scripting-engine string / array backing stores** — JS/VBScript string buffers and typed-array/`ArrayBuffer` backing stores *when the engine still routes through RtlHeap*: corrupt the stored length/capacity and you get an attacker-sized relative R/W window over the heap. (Note: V8, modern Chakra, and PartitionAlloc-based engines allocate outside RtlHeap — confirm the allocator first.)
- **Container backing buffers on realloc** — `CString`, `std::vector`/`std::basic_string` backing stores and similar: predictable sizes, frequently reallocated (so easy to groom), and carry a size/capacity field worth corrupting.
- **Objects with a leading vtable or embedded function pointer** — the control-flow target once you have a write, subject to CFG/XFG/CET (§3).

**Where NT-heap overflow bugs actually live (the complement of the Segment-Heap system-process list in §1):** the long tail of third-party Win32 desktop applications; document, image, font, and media **file-format parsers** (historically the richest seam); older line-of-business software built on classic MFC/ATL/COM; and mixed suites like Microsoft Office where *some* processes/heaps are now Segment Heap but plenty of parsing paths still hit the NT heap. The practical rule: UWP/MSIX apps and the fixed system-binary set are Segment Heap; almost everything else you'll be handed a bug in defaults to NT heap + LFH — but **fingerprint the specific heap the vulnerable allocation uses** (`FrontEndHeapType`, segment signature) rather than assuming by process.

### 2.7 Reliability and the practical difficulty today

Modern reliable heap exploitation is dominated by three problems: (1) **beating allocator non-determinism** (LFH randomization, Segment Heap address randomization) through grooming and by steering allocations to deterministic paths (§2.4); (2) **surviving encoded/validated metadata** by targeting object data instead of headers, or by using the encoding-tolerant VS `Allocated`/`UnsafeSize` quirks — or, with a key leak, by forging metadata outright (§2.5); and (3) **defeating the process-wide mitigations** (ASLR via an info leak, CFG/XFG/CET via data-only or carefully chosen call targets, ACG/CIG by keeping the payload data-only or out-of-process). Automated layout tooling (SLAKE, "Automatic Heap Layout Manipulation for Exploitation," Gollum, MAZE for automated feng shui, HeapHopper for model-checking allocator security) reflects how much of the difficulty is now in the layout search itself. The net effect: single-bug, metadata-only heap exploits are largely obsolete; reliable exploitation typically chains an info-leak + a data-corruption adjacency primitive + a CFI-aware control transfer.

### 2.8 Instrumentation and debugging (research aid — and anti-analysis tell)

The same tools that make heap research tractable are observable, which matters for the EDR angle in §4:

- **PageHeap / Application Verifier (`gflags`).** *Full* PageHeap places an inaccessible guard page immediately after each allocation, so a linear overflow faults at the exact instruction that writes past the end — invaluable for root-causing an overflow, and it also perturbs layout enough to break grooming. *Light* PageHeap uses fill patterns and suffix checks validated on free instead of guard pages. Enabled per-image via `gflags /i <app.exe> +hpa` (full) or `+ust` for allocation-stack capture. Because full PageHeap changes allocation sizes/placement and page protections wholesale, its presence is both a debugging aid and something exploit code can detect.
- **WinDbg heap walking (given the broken `!heap` on 11).** `!heap -p -a <addr>` resolves a single address to its chunk and allocation stack; `!heap -i` / `!heap -s` for interactive/summary views; and for Windows 11 where the extension misparses, walk structures directly with the data-model LINQ, e.g. `dx @$curprocess.Heaps` and `dx @$curprocess.Heaps.Where(h => h.Type == "SegmentHeap")`, or cast and traverse `_SEGMENT_HEAP`/`_HEAP` fields by hand. Segment-Heap-specific community WinDbg extensions exist to parse the VS/LFH/backend trees that `!heap` doesn't.

## 3. Mitigation internals

### 3.1 Heap metadata protections

**NT Heap (evolution):**
- *Safe unlinking* (XP SP2): before unlinking a free chunk, verify `E->Flink->Blink == E->Blink->Flink == E`, killing the classic unlink write-what-where.
- *Heap entry header cookie* (XP SP2): an 8-bit random value in each header validated on free.
- *Heap entry metadata randomization / Encoding* (Vista+): the whole `_HEAP_ENTRY` is XORed with `_HEAP.Encoding` (gated by `EncodeFlagMask = 0x100000`); the decode is validated by a checksum (the first three header bytes XORed must equal the fourth). This defeats *blind* header overwrites because you cannot forge a valid encoded header without the key — **but see §2.5: a leaked `Encoding` reopens it.**
- *FreeList[] removal / ListHint + bitmap* (Vista/7): the array-based `FreeList[]` that older techniques (Nicolas Waisman's FreeListInUse bitmap-flip, FreeList[0] attacks) relied on was removed in favor of `BlocksIndex`/`ListHint`.
- *Front-end hardening* (Win8): heap handle (`_HEAP`) free/realloc prohibited (killing Ben Hawkes' Vista `_HEAP`-reuse technique), randomized virtual-alloc locality, LFH non-determinism, encoded LFH offsets + interlocked cursor (killing the `FreeEntryOffset` attack, §2.2), fast-fail on corruption, guard pages, removal of the LFH `RtlpLowFragHeapAllocFromContext` try/catch that enabled brute-forcing, and arbitrary-free protection.

**Segment Heap (Yason's six mechanisms):** fast-fail on linked-list node corruption; fast-fail on RB-tree node corruption; heap address randomization (via `RtlpHpSegHeapAllocate`, making heap base guessing unreliable); guard pages (placed around subsegments/blocks so a linear overflow hits an unmapped page); function-pointer encoding; VS block-size encoding (the `Sizes` field, §2.3); and LFH subsegment `BlockOffsets` encoding + LFH allocation randomization. Critically, the Segment Heap's design **reduces inline metadata**: backend and large blocks have no header at the user block; LFH blocks have no header (bitmap instead). This both *reduces* the classic metadata-corruption surface and *changes* it — a linear overflow in LFH/backend corrupts neighboring **object data**, not allocator metadata, which is why adjacency grooming dominates.

### 3.2 Process-wide exploit mitigations relevant to the heap

- **ASLR / High-Entropy ASLR.** Heap base is randomized as part of ASLR (originally ~5 bits on 32-bit; HEASLR on x64 gives 24–32+ bits for bottom-up/top-down and heap allocations), making blind heap-spray-to-fixed-address (the `0x0c0c0c0c`/`0x0a0a0a0a` era) impractical on 64-bit and forcing an info leak.
- **DEP/NX.** Non-executable heap — you cannot execute sprayed shellcode directly; forces ROP/JOP or a data-only path.
- **CFG (Control Flow Guard).** Coarse-grained forward-edge CFI: a compiler-generated bitmap of valid indirect-call targets, checked before indirect calls. A violation raises `__fastfail(FAST_FAIL_GUARD_ICALL_CHECK_FAILURE)` = subcode `0x0A`. Limits: coarse (any valid function entry is allowed), does not protect return addresses, and is weakened when any module in the process is non-CFG. Default on Windows 11 x64 for CFG-compiled images.
- **XFG (eXtended Flow Guard).** Fine-grained CFG that checks a type-hash of the call prototype, narrowing valid targets. The `/guard:xfg` MSVC flag exists (since VS 2019 16.5) and XFG shipped on Insider builds, but **enforcement-by-default never shipped and XFG is effectively deprecated** in favor of CET per McGarr's BH USA 2025 talk; its fail-fast subcode is `FAST_FAIL_GUARD_ICALL_CHECK_FAILURE_XFG` = 64.
- **CET / Hardware-enforced Stack Protection (shadow stacks).** Intel CET / AMD Shadow Stack backward-edge CFI: a hardware-protected shadow stack stores return addresses; a mismatch on `ret` raises a **#CP control-protection fault** handled by `nt!KiControlProtectionFault`, terminating the process. User-mode shadow stacks are a per-process, opt-in mitigation via the `/CETCOMPAT` link flag; all native 64-bit Windows DLLs are built `/CETCOMPAT`. On Windows 11 24H2 on CET-capable hardware the default is `EnableUserShadowStack` in **compatibility mode** (fault fatal only when the unwinding module is `/CETCOMPAT`); strict mode makes all violations fatal. Windows uses only CET's shadow-stack feature, not IBT (forward edge is CFG's job). Kernel-mode CET is **off by default** on 24H2 and requires VBS+HVCI. Hardware-gated to Intel Tiger Lake+ / AMD Zen3+.
- **ACG (Arbitrary Code Guard)** and **CIG (Code Integrity Guard).** CIG (first in Edge, Win10 1511) enforces that only properly signed images load (via the `ProcessSignaturePolicy`/UMCI). ACG (Edge, Win10 1703) enforces process-wide W^X: no new executable pages, no RWX, no modification of existing code pages — it forces JIT engines out-of-process. Failure returns `STATUS_DYNAMIC_CODE_BLOCKED` (`0xc0000604`). Together they break the universal "load/generate native code" primitive, which is why ACG+CIG+CFG are co-dependent (Fratric's Project Zero work showed ACG is insufficient without a sound CFG). In Edge's enhanced-security mode CET and ACG are enabled in the renderer.

### 3.3 What breaks, what remains

Encoded headers + safe unlinking + list/tree fast-fail kill the classic *blind metadata-overwrite → arbitrary write* primitives on both allocators. LFH randomization + guard pages break *deterministic adjacency to metadata* and make linear overflows into unmapped pages a crash rather than a corruption. ASLR/HEASLR breaks *blind spray*. DEP + ACG + CIG break *direct shellcode/JIT*. CFG/XFG/CET raise the cost of *control-flow hijack* via corrupted pointers/vtables.

What remains exploitable: **data-only corruption** (length/size fields, type tags, non-code pointers, permission flags) that never touches a validated header and never hijacks control flow — invisible to CFI; **overlapping-chunk/type-confusion** primitives (VS allocator attack, LFH object-data overflow) that corrupt object data; **forged-metadata corruption once the encode keys are leaked** (§2.5); **info-leak-then-corrupt** chains that defeat ASLR; and **allocation-overlap** that yields relative/arbitrary R/W which can then be used to overwrite data that CFG doesn't cover (e.g. data pointers consumed before an indirect call, or targets reached through a legitimate CFG-valid function).

## 4. Defensive / detection (EDR perspective)

### 4.1 Mitigation-triggered terminations as the primary high-fidelity signal

The most reliable heap-exploitation signals an EDR gets are the **fail-fast terminations** the mitigations raise, surfaced through Windows Error Reporting / the Watson Feedback Platform:

- **`__fastfail` / `RtlFailFast`.** Per Microsoft Learn, a user-mode fast fail appears as a **second-chance non-continuable exception with code `0xC0000409` (STATUS_FAIL_FAST_EXCEPTION)**, the first exception parameter being the FAST_FAIL subcode. Critically, **fast-fail bypasses all SEH/VEH handlers and invokes WER directly** — which both guarantees a kernel/WER-visible signal and means an application's own in-process crash reporter may never run. The subcode disambiguates the cause: `FAST_FAIL_HEAP_METADATA_CORRUPTION` = **50**, `FAST_FAIL_CORRUPT_LIST_ENTRY` = 3 (heap/linked-list unlink corruption), `FAST_FAIL_GUARD_ICALL_CHECK_FAILURE` = `0x0A` (CFG), `FAST_FAIL_GUARD_SS_FAILURE` = 44 (shadow stack), `FAST_FAIL_GUARD_ICALL_CHECK_FAILURE_XFG` = 64, `FAST_FAIL_ETW_CORRUPTION` = 61. (The numeric FAST_FAIL table is from `winnt.h`; Microsoft documents the mechanism and `0xC0000409` but not the full subcode schema, so treat subcodes as community/header-corroborated.)
- **`STATUS_HEAP_CORRUPTION` = `0xC0000374`.** Raised by the heap manager (crash in `ntdll!RtlReportFatalFailure`/`RtlpLogHeapFailure`) when corruption is detected under **HeapEnableTerminationOnCorruption** (the default for most processes on modern Windows; also exposed as the WDEG "Validate heap integrity" mitigation, which "terminates a process when heap corruption is detected"). Confirmed reproducing on Windows 11 24H2.
- **WER/Watson plumbing.** `WerFault.exe -u -p <pid>` spawning against a monitored process is itself an observable crash signal; the `Report.wer`/failure bucket carries the exception code, faulting module (frequently `ntdll.dll`), fault offset, and the P-parameter subcode. WER **LocalDumps** (`HKLM\...\Windows Error Reporting\LocalDumps`) lets an EDR/IR capture a full dump of the faulting process. Observed Windows 11 24H2 CFG buckets look like `FAIL_FAST_GUARD_ICALL_CHECK_FAILURE_c0000409_<module>!<func>`.
- **CET #CP faults** surface as a fast-fail-class `0xC0000409` termination with the CET subcode; the kernel handles the #CP in `nt!KiControlProtectionFault` before terminating.

### 4.2 Memory-operation telemetry (post-exploitation)

Because the overflow itself is often silent, the next-best signals are the **post-corruption memory operations** an exploit performs to stage a payload:

- **ETW Threat-Intelligence (`Microsoft-Windows-Threat-Intelligence`, ETW-TI).** The primary kernel memory-op sensor for EDR. Kernel sensor functions include `EtwTiLogAllocateVirtualMemory`, `EtwTiLogProtectVirtualMemory`, `EtwTiLogMapViewOfSection`, `EtwTiLogReadWriteVm`, `EtwTiLogQueueApcThread`, `EtwTiLogSetContextThread`. Per event an EDR sees the calling/target PID, base address, region size, protection flags, and a user-mode call stack — directly catching the canonical `NtAllocateVirtualMemory(RWX) → NtWriteVirtualMemory → NtProtectVirtualMemory(RX)` staging and any transition to `PAGE_EXECUTE_*`. Limits: ETW-TI is **event-based and retroactive** (e.g. the bytes written by `NtWriteVirtualMemory` are not captured) and is **PPL-gated** — a consumer must run as a PPL antimalware-light process (enforced in `EtwpCheckNotificationAccess`/`RtlTestProtectedAccess`) via a Microsoft-co-signed ELAM driver, so only properly-signed EDRs can subscribe.
- **ETW heap tracing (`+ust`, WPT `-heap`, `ETW_HEAP_EVENT_ALLOC/FREE/REALLOC`).** Microsoft documents retail heap allocation/free/realloc ETW events and stack-walking heap captures (`xperf -heap -Pid … -stackwalk HeapAlloc+HeapRealloc`; GFLAGS `+ust`). These are heavyweight per-image diagnostic instruments (IFEO-gated, big perf cost), **not** fleet-wide EDR telemetry — useful for IR/repro of a heap bug, not live detection at scale.

### 4.3 Heap-spray / grooming heuristics and the mitigation-as-signal era

- **Content/rate heuristics.** Microsoft Research's NOZZLE (Ratanaworabhan, Livshits & Zorn, USENIX Security, Aug 10 2009) interpreted heap objects as x86 and computed a "heap health" metric to flag sprays; the authors report that "the performance overhead of NOZZLE is less than 7% on average," detecting "12 published and 2,000 synthetically generated heap-spraying exploits" with "no false positives when run over 150 popular Internet sites," while explicitly conceding attackers can stay under the threshold and that sprayed data can resemble legitimate code. Heap Taichi (CCS 2010) demonstrated fragmenting shellcode and abusing the 64K allocation granularity to evade NOZZLE-style detectors. Entropy-based spray detectors exist largely as vendor IP/patents. Browser telemetry can flag extreme heap-growth rates or JS loops minting large numbers of typed arrays, and EDRs watch for a process suddenly allocating many identical blocks.
- **EMET → WDEG.** EMET (EOL July 31, 2018) folded into Windows Defender Exploit Guard (WDEG) in Windows 10 1709. WDEG's exploit-protection surfaces Event Viewer **Security-Mitigations** events and Defender for Endpoint advanced-hunting ActionTypes: e.g. EID 12 "Code integrity guard block," EID 13/14 EAF audit/enforce, EID 15/16 EAF+ audit/enforce (`ExploitGuardEafViolationAudited`/`…Blocked`). **EAF/EAF+** (export/import-address-table access filtering via guard-page/debug-register traps) is a genuine shellcode-behavior detector that shipped. The dedicated **HeapSpray** pre-allocation mitigation (reserving common spray addresses) survives as a legacy per-app knob but was largely made redundant by HEASLR on 64-bit. "Validate heap integrity" is the shipping WDEG surface of termination-on-corruption.
- **Mitigations as detection, not just prevention.** Every fail-fast bucket (heap metadata, CFG, CET, EAF) is both a prevention (process dies) and a telemetry event. A mature EDR correlates the WER/Security-Mitigations event, the WerFault spawn, and preceding ETW-TI allocation/protect anomalies to distinguish an exploitation attempt from a benign crash.

### 4.4 Limits of detection and evasion

- **Data-only / data-oriented attacks.** A heap overflow that corrupts a length field, type tag, or non-code pointer yields a primitive **without any crash and without any control-flow violation** — invisible to CFG/XFG/CET/GS and to heap-metadata fast-fail. This is the single biggest detection blind spot and precisely where modern Segment-Heap exploitation lives (no inline LFH header to corrupt → overflow hits object data). No CFI variant detects a DOP attack because no control flow is hijacked.
- **Grooming is indistinguishable from legitimate allocation.** Precise feng shui uses the target's *own* normal allocation paths and size classes; range-based sprays populate the allocator's legitimate buckets. These artifacts are hard to see in production and typically only show in post-mortem memory forensics on a crashed process.
- **`0xC0000409` is noisy.** `FAST_FAIL_FATAL_APP_EXIT` (7) is used benignly by `abort()`/Rust panics, so the exception code alone is not an exploitation indicator — the EDR must read the subcode (50 = heap, 0x0A = CFG, etc.) to disambiguate.
- **Telemetry blinding.** User-mode ETW (`ntdll!EtwEventWrite`/`NtTraceEvent`) can be patched in-process to blind user-mode providers; this does **not** blind kernel ETW-TI, but a Ring-0 attacker (BYOVD) can disable ETW-TI callbacks or unregister the EDR's kernel consumer. Windows can itself fast-fail (`FAST_FAIL_ETW_CORRUPTION` = 61) on ETW structure tampering, which is a tamper signal in its own right.

## 6. State of the art and hardest open problems

The practical state of the art is: **groom for adjacency, corrupt application data (not metadata), leak to beat ASLR, then achieve a CFI-aware control transfer or stay fully data-only.** Blind inline-metadata exploitation is essentially a solved defensive problem on both allocators — *conditioned on the encode keys staying secret*; a sufficiently strong read primitive leaks those keys and reopens forged-metadata corruption (§2.5). The Segment Heap's header-less LFH/backend design simultaneously shrank the metadata attack surface and shifted all the pressure onto object-data corruption and allocator layout control. The VS allocator's encoded-but-coalescing-tolerant size fields remain the most interesting *metadata* avenue (Blue Frost), but even that produces an overlap primitive against object data.

The hardest open problems, from both sides:

1. **Reliable adjacency against randomized front ends.** LFH allocation randomization and Segment Heap address randomization make deterministic placement probabilistic; exploit reliability engineering (and automated layout search) is where most offensive effort now goes, and it is inherently target-specific.
2. **Data-only attacks are undetectable by current CFI.** Neither CFG/XFG nor CET observes a corrupted length/type/data-pointer; building defenses (and detections) for data-oriented programming without prohibitive cost is unsolved.
3. **Detecting grooming without drowning in false positives.** Grooming is behaviorally identical to legitimate heavy allocation; content/rate heuristics (NOZZLE-style) are evadable and noisy, and the high-fidelity signals only fire *after* a mitigation trips — i.e. after the bug has already been exploited or crashed.
4. **Telemetry integrity under a kernel adversary.** ETW-TI is the best memory-op signal but is PPL-gated and defeatable by BYOVD; preserving telemetry against a Ring-0 attacker is an arms race (reflected in Microsoft's push toward VBS/HVCI-backed enforcement and the move of CET/CFG into the kernel).
5. **Memory-safety as the only structural fix.** The direction of travel — V8 heap sandbox, type-isolation arenas in engine allocators, hardware tags (MTE on ARM) — points at structural memory safety rather than more allocator hardening, because each incremental allocator mitigation has been met by a shift to the next adjacency/data-only technique.
