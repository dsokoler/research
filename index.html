01

Overview

WESP is a single Microsoft-signed kernel driver that centralizes the security callbacks an antivirus or EDR vendor would otherwise implement in its own driver, then exposes them to user-mode clients through a rule-filtered event subscription API.

The driver, wesp.sys, registers as a file system minifilter and hooks process, thread, image-load, object-handle, and registry callbacks. It funnels everything through one named communication port. The client library, espclient.dll, lets a user-mode process register itself, declare filter rules, and receive only the events those rules match.

Three characteristics shape everything else in this report:

  • Rules are evaluated in the kernel. A client declares boolean expressions over typed kernel objects. The driver evaluates them inline, on the thread performing the operation, and queues only matches. Clients never see the firehose.
  • The driver enforces; delivery is separate. File pre-operation callbacks return a deny status selected by rule processing, including STATUS_VIRUS_INFECTED, so operations can be blocked synchronously. Event delivery to a client is asynchronous and independent of that decision. Whether a third-party client's rules can drive a deny, or only Microsoft's policy can, is unresolved. See §4.
  • Both components are largely Rust. wesp_lib in the driver and espclient_rs in the client do the real work, wrapped in thin C++ shims that add telemetry and reference counting. Those shims also translate between the public ABI and the internal representation, which matters if you plan to build on this platform.

Where RemoteClient and IpAddress come from

These resolve the otherwise homeless IpAddressComparison, and the mechanism is extra create parameters rather than any network stack integration confirmed.

The driver imports the full ECP API set: FltGetEcpListFromCallbackData, FltFindExtraCreateParameter, FltGetNextExtraCreateParameter, FltIsEcpFromUserMode, FltAcknowledgeEcp, FltInsertExtraCreateParameter, and the allocation helpers. EcpList is also one of the nine field value kinds, so ECP contents are directly addressable from a rule.

When a file is opened over SMB, the server attaches an extra create parameter describing the originating client, including its network address. That's the path by which a file event carries an IP. So the capability is remote-access attribution on file operations: you can write a rule such as "a write to this share arriving from outside this address range." It is not connection filtering, packet inspection, or any visibility into traffic that doesn't terminate in a file operation. The distinction matters when scoping what WESP replaces, covered in §12.

The communication port

One port, \EspFilterPort, is created with FltCreateCommunicationPort confirmed. It's the only entry point into the driver from user mode. The driver also imports FltBuildDefaultSecurityDescriptor, so the port is access-checked rather than open to any caller inferred. This analysis didn't recover the specific ACL.

Internally, wesp::server and wesp_lib::client::manager::ClientManager track each connecting subsystem as a registered client. Registrations persist to disk through PersistedStore, so client identity survives a reboot. Live connections are tracked per process in ConnectedClientProcesses, keyed by KPROCESS.

04

How a client receives events

Registration is separate from the live channel, and the live channel uses overlapped I/O over the filter port.

  1. Register. EspRegisterClient builds a versioned message and calls FilterConnectCommunicationPort(L"\\EspFilterPort", ...) once, then closes the handle. The manifest names the payload fields: ClientName, ClientId, and Altitude confirmed. Altitude is the minifilter load-order concept, so clients are explicitly ordered against one another in the callback stack.
  2. Connect. EspConnectEventQueueWithIocp or EspConnectEventQueueWithCallback opens the event queue and returns a handle you bind to an I/O completion port.
  3. Arm. EspArmEventNotification posts an overlapped read through Esp::PortListener::ArmIo, using a 0x1010-byte buffer framed as a FILTER_MESSAGE_HEADER plus payload.
  4. Receive. Each completed I/O is one matched event, already filtered in the kernel against your active rules.
  5. Complete. EspCompleteEventNotification releases the notification's slot against your memory budget.

Every exported call instruments itself through a WespClientProvider ETW activity, so a client's API usage is visible to anything consuming that provider.

Where latency enters, and where it doesn't confirmed

Tracing EspFsFilePreCreate through the queue internals shows exactly where delay can occur.

  • Rule matching is synchronous and inline. The hook reads two flags first and returns immediately if no client subscribes to that event type. Otherwise it builds the event object and calls EventDispatcher::process_rules_with_current_thread_process<FileCreate> on the thread performing the file operation. This cost scales with active rule count, but it's in-memory evaluation with no cross-process communication.
  • Queuing doesn't block. AsyncStateInner::enqueue inserts into the client's notification list under a push lock, checked against a running memory counter and a cap. Success and over-budget return distinct status codes. The driver never grows the queue without bound and never blocks the producing thread.
  • Delivery pushes, it doesn't poll. Each queue has its own delivery worker, created with PsCreateSystemThread, which blocks on a KEVENT via KeWaitForSingleObject while the queue is empty. Enqueueing signals that event, the worker wakes, dequeues, and calls FltSendMessage, which completes your pending receive. That explains the KeSetEvent in the enqueue path: the producing thread hands off to the worker rather than delivering inline. There's no polling interval anywhere.
  • The gap is your own idle time. If you're busy handling the previous notification and haven't re-armed, the next match waits in the queue. Past the cap, you lose events. The system doesn't stall.

What happens at the cap confirmed

AsyncStateInner::enqueue drops the newest event and preserves the queue. There is no eviction loop, no head removal, and no ring-buffer wraparound:

charge = (chunk_count << 16) | 0x1000;
if (usage + charge <= MaxCapacityBytes) {
    usage += charge; /* insert, return 0x2b queued */
} else {
    drop(new_entry);  /* return 0x18 over budget; usage unchanged */
}

Three consequences. History survives, the present is lost, so a saturated queue keeps its oldest events and discards current activity until the client drains it, which for detection is the wrong half to keep. The budget is in synthetic units, not bytes: a flat 4096 per notification plus 65536 per buffer chunk, against chunks drawn from a 4096-byte lookaside list, so the accounting over-charges chunked notifications by roughly 16×. Size queues by measurement, not arithmetic. And nothing counts the drop — the usage counter simply isn't advanced, so no site exists that could maintain a lost-event total.

Two smaller behaviors from the same function: a param_4 flag selects insert-at-head instead of append-at-tail, giving a priority path; and a notification whose ID is already present returns 0x19 and is discarded, so IDs are deduplicated. Other statuses are 0x27 arithmetic overflow, 0x20 allocation failure, and 0x26 insert-failed-with-rollback.

Lifetime scopes confirmed

Lifetime appears on EspCreateEventQueue, EspCreateCollection, EspEnumerateRuleIds, EspEnumerateCollectionIds, EspEnumerateEventQueueIds, and EspRemoveRulesForClient. Queues, collections, and rules are each created under a lifetime scope and can be enumerated by that scope. This is the API counterpart to the driver's PersistedStore: some state is transient to the session, and some survives.

The driver can deny operations confirmed

Delivery to a client is asynchronous, but that's separate from whether the operation is allowed to proceed. The driver decides that synchronously, before it returns.

A callback ends by selecting its return value from a five-entry table at 0x1803bb230, indexed by a verdict byte. The verdict is the return value of the call to EventDispatcher::process_rules_with_current_thread_process, and the selection is a bounds check followed by an eight-byte-stride load:

cmp   bpl, 4
ja    allow                      ; verdict > 4 means no objection
movzx eax, bpl
lea   rcx, [rip+0x39d119]        ; 0x1803bb230
mov   rdi, [rcx+rax*8]           ; {flag, NTSTATUS}

Clients set the action, and nothing gates which one confirmed

The verdict originates in a matching rule's action, which the client supplies. Three findings together settle that a third-party client can request a deny.

The ordinal travels from the client's rule structure into the dispatch untouched. In Rule::from_incoming_internal:

movups xmm0, [r8+0x130]        ; copy the incoming action (32 bytes)
movups xmm1, [r8+0x140]
movaps [rsp+0x30], xmm0
movaps [rsp+0x40], xmm1
mov    dword [r8+0x130], 2     ; reset source: Rust moved-out sentinel
mov    r9d, [r8+0x188]         ; event type, passed alongside
lea    rcx, [rsp+0xa8]
lea    r8,  [rsp+0x30]
call   RuleAction::from_incoming

[r8+0x130] is the client-supplied rule. There is no bounds check, no tier check, and no privilege comparison at this call site. RuleAction::from_incoming is itself a bare jump table, mov eax,[r8] then movsxd rax,[r10+rax*4] then jmp rax, with no range test of its own, which is ordinary Rust codegen for a match over an enum already validated during message deserialization. The table carries at least 40 arms; some write a discriminant and return with no payload, and some branch on event-type ranges before constructing one.

No capability check covers actions. CapabilityTier has exactly two methods in the whole driver, verify_property_query and thread_has_restricted_property, both concerned with reading properties. There is no action equivalent. The other capability function, ClientMessage::verify_capabilities, gates message types, meaning whether you may create a rule at all, not what the rule does when it matches.

Only one action is restricted, and the restriction is about persistence. ForceAllow's guard lives in InternalClient::persisted_store_rule with the message that it is an internal action and should not be persisted. Singling out one action implies the rest are not internal.

Read together with STATUS_VIRUS_INFECTED sitting in the deny table, which is an antimalware verdict rather than an internal housekeeping status, the conclusion is that blocking is available to any client that can create a rule, across file, section, volume, registry, and handle operations.

What remains open is narrow and cosmetic: which integer ordinal selects which verdict. The action-discriminant to verdict-byte edge inside the engine was not traced, so the example in §9 still shows a plausible ordinal rather than a recovered one. The structural question, whether a gate exists, is answered, and the answer is that none does.

Two corrections, and the same reasoning error behind both. Earlier readings of this report held that the driver can't block, and then that a third-party deny was gated behind an unrecovered capability policy. The first reasoned from a missing FltCompletePendedPreOperation import, which is needed only to pend an operation and complete it asynchronously, not to deny synchronously. The second reasoned from the existence of a CapabilityTier concept to the assumption it covered actions; enumerating its complete method set showed it doesn't. Both were absence-of-evidence errors, and they share a lesson with the import-table point in §10: a mechanism's presence or absence in an import table is not evidence of what it is used for.

06

The filter and rule engine

A filter is one predicate node: either a leaf that compares a property of an object, or a boolean combination of two other filters. A rule is a compiled, GUID-identified filter tree installed against a client. Only events that satisfy an active rule reach that client's queue, and the evaluation happens in the kernel.

Grammar

Filter ::= Leaf(ObjectType, PropertyId, ComparisonType, Value)
         | NOT(Filter)
         | AND(Filter, Filter)
         | OR(Filter, Filter)
         | XOR(Filter, Filter)

The types constrain the unnamed properties hard. File exposes exactly one String property, at ID 17, which is almost certainly the path. Thread carries two MemAddr properties, the natural fit for a start address and a TEB or stack base, which is the raw material for injection detection. This identifies FilterType 0xD. Two IpAddress properties and four Port properties make it a network endpoint, and the symbol table names it outright: espclient_rs::filter::network::NetworkConnectionFilterDescriptor confirmed. There is a whole filter::network module. The rule engine models network connections as a first-class filterable object, with dedicated IpAddress and Port comparison kinds to match. It has no exported EspCreate*Filter wrapper in this build, and the driver has no network data source (§12), so the schema is built out ahead of the plumbing.

The extraction also surfaced two comparison value kinds not visible elsewhere: PortComparison and TokenGroupsComparison, bringing the client-side total to fourteen.

Comparison operators confirmed

ESP_COMPARISON_TYPE has exactly 19 values, 0 through 18. EspRsCreateFilter bounds-checks the field with < 0x13.

The driver evaluates comparisons through three value-kind-specific functions in wesp_lib::filter::comparison: evaluate_numeric_op, evaluate_string_op, and BinaryComparison::evaluate_op. Each dispatches on an operator byte read straight off the wire through read_zerocopy, so the wire value is the Rust discriminant with no translation.

On the client side, DataComparison::try_from_raw validates the ordinal against the property's value kind before handing off.

Collections

A collection is a typed, driver-persisted set. The driver implements binary, integer, and string collections, the last with pattern compilation for wildcard entries. You push one into the driver with EspCreateCollection and EspUpdateCollection, then enumerate it with EspEnumerateCollectionEntries. Creation takes a Type, a Lifetime, and StringFlags.

Collections matter because a filter predicate can reference one directly through open_collection_for_predicate. This is the allow-list and deny-list primitive: you can express "block if this hash is in my blocklist" as a leaf that tests set membership in the kernel, with no round trip to user mode per event.

Two examples: one that observes, one that blocks. Property IDs and comparison constants are placeholders throughout inferred, since property names aren't recoverable from these binaries. The call shapes, tree structure, event scoping, and verdict mapping are confirmed.

An observational rule

Notify on file writes under C:\Windows\System32\ when the writing process isn't Microsoft-signed, excluding .tmp files.

// Leaf filters
EspFilterHandle hPathFilter;
EspCreateFileFilter(FILE_PROP_PATH, ESP_CMP_STARTS_WITH,
                     L"C:\\Windows\\System32\\", &hPathFilter);

EspFilterHandle hExtFilter;
EspCreateFileFilter(FILE_PROP_EXTENSION, ESP_CMP_EQUAL,
                     L".tmp", &hExtFilter);

EspFilterHandle hNotTmp;
EspCreateNotFilter(hExtFilter, &hNotTmp);

EspFilterHandle hSignerFilter;
EspCreateProcessFilter(PROCESS_PROP_SIGNER, ESP_CMP_NOT_EQUAL,
                        &SignerMicrosoft, &hSignerFilter);

// Event scoping lives in the tree, not in EspUpdateRules
EspFilterHandle hEventFilter;
EspCreateEventFilter(EVENT_PROP_TYPE, ESP_CMP_EQUAL,
                      &EVENT_TYPE_FILE_WRITE, &hEventFilter);

// Compose the tree
EspFilterHandle hPathAndNotTmp, hWithSigner, hFinal;
EspCreateAndFilter(hPathFilter, hNotTmp, &hPathAndNotTmp);
EspCreateAndFilter(hPathAndNotTmp, hSignerFilter, &hWithSigner);
EspCreateAndFilter(hWithSigner, hEventFilter, &hFinal);

// Compile and install
EspRuleHandle hRule;
EspCreateRule(hFinal, &hRule);

ESP_RULE_UPDATE_ENTRY entry = { .op = 1, .rule = hRule };
EspUpdateRules(hClient, ESP_RULE_UPDATE_FLAGS_NONE, 1, &entry);

A blocking rule

The first example observes. This one denies: refuse to open any file whose hash appears in a blocklist, and report it as infected. It exercises the parts of the engine that make WESP more than a telemetry feed, namely kernel-side collection membership and the deny verdict.

Read the confidence markers carefully here. The filter tree, the collection mechanism, the event type, and the verdict mapping are all confirmed. The path by which a client sets a rule's action is not, as covered in §12, so the action assignment below reflects the most likely reconciliation rather than a recovered signature.

// 1. Push a blocklist into the kernel. Binary collection of file hashes.
EspCollectionHandle hBlocklist;
EspCreateCollection(hClient, ESP_COLLECTION_TYPE_BINARY,
                     ESP_LIFETIME_PERSISTENT, 0, &hBlocklist);
EspUpdateCollection(hBlocklist, knownBadHashes, hashCount);

// 2. Leaf: this file's hash is in that collection.
//    Binary value kind, so InCollection is ordinal 3.
EspFilterHandle hBadHash;
EspCreateFileFilter(FILE_PROP_HASH, ESP_CMP_IN_COLLECTION,
                     hBlocklist, &hBadHash);

// 3. Leaf: scope to file-open events.
EspFilterHandle hOnOpen;
EspCreateEventFilter(EVENT_PROP_TYPE, ESP_CMP_EQUAL,
                      &ESP_EVENT_TYPE_FO_OPEN, &hOnOpen);

// 4. Compose.
EspFilterHandle hFinal;
EspCreateAndFilter(hBadHash, hOnOpen, &hFinal);

// 5. Compile with a deny action.
//    The action field is confirmed; the ordinal's spelling is not.
ESP_RULE_DESC desc = {
    .filter       = hFinal,
    .event_type   = ESP_EVENT_TYPE_FO_OPEN,
    .action       = ESP_ACTION_DENY_VIRUS_INFECTED,  // verdict 0
    .enabled      = TRUE,
    .is_top_level = TRUE,
    .order_group  = 0,
    .lifetime     = ESP_LIFETIME_PERSISTENT,
};

EspRuleHandle hRule;
EspCreateRule(&desc, &hRule);

ESP_RULE_UPDATE_ENTRY entry = { .op = 1, .rule = hRule };
EspUpdateRules(hClient, ESP_RULE_UPDATE_FLAGS_NONE, 1, &entry);
              AND                         action: deny
             /   \                       verdict 0 -> STATUS_VIRUS_INFECTED
   File.Hash      Event.Type == FO_OPEN
   in collection
   (blocklist)

On a match, process_rules_with_current_thread_process returns verdict 0, and EspFsFilePreCreate selects the corresponding entry from the deny table. The caller's CreateFile fails with STATUS_VIRUS_INFECTED, surfacing in Win32 as a virus-detected error. Choosing verdict 2 instead returns STATUS_NOT_FOUND, which makes the file appear absent rather than blocked, and verdicts 1, 3, and 4 return STATUS_ACCESS_DENIED.

Three properties of this rule are worth noting, because they're what a predicate language alone wouldn't give you. The blocklist lives in the kernel, so membership is tested in the I/O path with no round trip to your process. The decision is synchronous, so the file never opens rather than being reported after the fact. And with ESP_LIFETIME_PERSISTENT, both the collection and the rule survive a reboot, so protection resumes before your agent starts, which is the one part of the boot-coverage gap this design does address.

Security considerations

  • Trust comes from the token, not the file. The message dispatcher calls PsReferencePrimaryToken on the connecting process, then AccessTokenHandle::query_security_attributes, and feeds the result into wesp_lib::capability::CapabilityTier confirmed. Client trust is a claims check against the process token rather than an Authenticode check on the binary. That's a meaningfully different model from "is this file signed by Microsoft."
  • The gate is a token claim named WESP://Permission confirmed. The driver reads the connecting process's primary token and looks for that security attribute, which holds one of two 64-bit values rather than a boolean: 10000000 admits a caller without further requirements, and 1000000000 additionally requires the process to be an Antimalware protected process, verified through ProcessProtectionInformation against protection level 0x31 (see credits). That is the concrete policy behind the CapabilityTier machinery this analysis found: a permission class, not a yes-or-no flag.
  • Test signing opens a development path. On a test-signed preview build, an elevated process can connect with neither the WESP://Permission attribute nor Antimalware PPL. The port's own access control still applies. Treat this as a development affordance, and as a reason not to draw production conclusions from test-signed experiments.
  • Checks run per connection, not per message, and the connection object is the credential. Token and protection checks happen when a connection to \EspFilterPort is established, including the short-lived connections used for registration, unregistration, and enumeration. The resulting CapabilityTier is stored in the pool block the connect callback returns as the filter manager's connection cookie. message_notify_callback then dereferences that cookie and dispatches, with no call to PsGetCurrentProcess, PsReferencePrimaryToken, or any protection query in the path confirmed. Later requests are checked for whether that connection is permitted the operation, which is what ClientMessage::verify_capabilities implements, never for who is making them. Since the connection is an ordinary file object, authority travels with the handle. See §13.
  • The per-message capability check is coarse. CapabilityTier::verify_property_query reads as if (tier != 0) return jumptable[query.kind](...); return 8;. Tier 0 is denied outright, and that comparison is the only test against the tier value in the function. The dispatch table has 15 arms for 15 property-query kinds, each walking the requested property list and rejecting on the first element that fails that kind's validity predicate.
  • Registration persists. Client identity records survive a reboot through PersistedStore, which makes them a forensic artifact worth locating on a live system. It shows what has ever registered, not only what's connected now. Its location, format, and protection are covered below.
  • A hostile registration is a denial-of-service primitive, not just a visibility problem. Clients set the rule action, and no capability tier gates which action they choose (§4). An attacker who can register a client can therefore install blocking rules across file, section, volume, registry, and handle operations. Denying handle opens against a chosen process, or file creates under a chosen path, is expressible in the same language a defender uses. Model a malicious client as able to stop work, not merely watch it.
  • Built-in observability cuts both ways. Every Esp* call logs to the WespClientProvider ETW provider. That's a ready-made monitoring point for defenders, and it also means any client's usage pattern is visible to anything else consuming the provider.
  • The port is access-controlled, and capped. It's created with FltBuildDefaultSecurityDescriptor(&sd, FLT_PORT_ALL_ACCESS), which restricts access to Administrators and SYSTEM, and with a maximum of 512 concurrent connections (see credits). The connect callback then applies the token checks above, so the ACL is the first of two gates rather than the only one.
  • Altitude gates participation. Clients register with an altitude, the same load-order concept minifilters use. Expect altitude allocation to be a prerequisite for shipping on this platform, as it is for minifilters today.

Client identity is a bearer GUID

Once a caller is through the connection gate, a client GUID is the only thing identifying a client, and cross-client operations are not scoped to the caller. Five pieces of evidence converge.

  • RegisteredClients::find_by_id, which the connect handler calls to resolve a client, compares the 16 GUID bytes and a liveness state byte. It performs no comparison against the calling process, token, or any owner field confirmed.
  • EspUnregisterClient doesn't use an established connection. It builds a 20-byte context of {opcode 2, target GUID} and opens a fresh connection to \EspFilterPort, then closes it. There is no handle to prove prior ownership and none is requested confirmed.
  • The driver does maintain a per-process association, ConnectedClientProcesses, mapping a process to the set of client GUIDs it has connected. That's a real ownership primitive, but it isn't used as one. Its lookup, contains_client, has exactly one code cross-reference in the entire driver, from a boolean-property reader inside event::args::process::ProcessArgument. It answers a rule predicate, letting a rule match on whether the subject process is itself a WESP client. It is telemetry, not authorization confirmed.
  • A symbol sweep for ownership-check primitives turns up nothing applicable. The only owner-related routines in the driver, ThreadArgument::owning_process, AccessTokenHandle::owner_sid, and the security-descriptor owner accessor, all read properties of the event subject for rule evaluation. None compares a caller against a client record confirmed.
  • The published proof-of-concept unregisters a client from a separate process invocation than the one that registered it, and it works (see credits). Any per-process ownership check would break that supported workflow.

Because EspEnumerateRegisteredClients hands out the GUIDs, the sequence is simply enumerate, then act. EspConnectClient likewise takes a bare GUID, so obtaining a management handle for another vendor's client follows the same path, and from there EspRemoveRulesForClient and EspRemoveAllRulesForClient operate on that handle.

Why this matters, and what it doesn't mean. This is not privilege escalation. Reaching the port already requires Administrator or SYSTEM, and the WESP://Permission claim can only be placed on a token with roughly SYSTEM-level privilege in the first place. What it changes is what an attacker who already holds that position, or a malicious client holding the lower permission class, can do to other security products. Unregistering a competitor's consumer is a supported API call that touches neither their process, their files, nor their driver, and unregistration is persisted, so the effect survives a reboot. An agent blinded this way may keep running and look healthy while receiving nothing. Compared with killing a protected process, it is quieter, more durable, and leaves different forensic traces.

The mitigation available to a vendor today is to treat its own registration as monitored state: enumerate periodically, watch the WespClientProvider ETW provider for unregistration activity, and re-register on loss. A platform-side fix would bind a registration to the identity that created it, or require the management connection to prove possession of something other than a value the API itself publishes.

Queue backpressure as an evasion primitive

The flow-control design in §4 has a security consequence worth stating directly: flooding a client's queue can create a window in which real detections are dropped. The mechanism is confirmed; treat the exploitability assessment as reasoned rather than tested, since no dynamic analysis was performed.

Four properties combine badly.

  • The budget is fixed at creation. MaxCapacityBytes is set in EspCreateEventQueue, and no export raises it afterward confirmed. A client under pressure can drain faster, but it can't grow its own headroom.
  • Events come from ordinary, unprivileged activity. File opens, registry queries, and thread creation are what the catalog covers, and any process can issue them in a tight loop. An attacker doesn't need privilege to generate matching events, only to guess or infer what the victim's rules match. Broad rules such as "all process creation" or "writes under this directory" are both common and easy to trigger.
  • Over budget means not delivered. The enqueue path returns a distinct over-budget status and the notification isn't queued confirmed. The operation still happens; the client just never hears about it.
  • Nothing counts the drop confirmed. The over-budget path discards the entry without advancing the usage counter, so there is no site that could maintain a lost-event total, and no such counter exists elsewhere in the driver. A client can tell it's under pressure; it can never learn what it missed.
  • Drops are newest-first confirmed, so a flood erases current activity while preserving the backlog (§4). An attacker doesn't rewrite history, but they do open a blind window that lasts from saturation until the client drains.

The economics favor the attacker. A flooding thread pays one syscall per event and, because rule matching is synchronous, absorbs the rule-evaluation cost on its own thread. The victim pays event construction, queue insertion, an IPC hop, and user-mode processing for every event that matches. That asymmetry is amplification, and the self-throttling effect on the attacker is easily offset by using more threads.

Two structural aggravations. Budgets are per client, so one client's flood can't starve another, but a single burst of system activity hits every client at once because they all observe the same events. And a client has no way to tell the kernel to slow down, because the producer is the operating system servicing another process's work.

Why this matters more here than for a driver. A vendor driver evaluating inline has no delivery window to miss: it reaches a verdict before the operation completes. WESP's asynchronous, lossy delivery introduces a gap that didn't previously exist, and load shedding is the client's responsibility. The practical mitigation is to treat sustained watermark crossings as an alert in their own right. Being flooded is itself a signal, and a client that logs threshold transitions turns an evasion attempt into a detection.

The persisted store

Registrations, rules, collections, and event-queue definitions survive reboots, in the registry rather than on disk confirmed. The wesp_lib::persistence::registry module wraps the key and value operations and the driver imports the matching Zw* APIs. This is also what lets the platform run a client's policy while the client isn't running (§12).

Path builders in PersistedStore compose a fixed hierarchy from string constants; decoding them and matching the lengths each builder passes pins the structure exactly. Formatting

Scalars store natively as registry values. Structured data stores as binary and parses back through typed schemas (StoredPredicate, StoredCollectionData, StoredCollectionRegion, CollectionSchema), with collection payloads written in regions. Writes are transactional confirmed: StoreTransaction is backed by ZwCreateRegistryTransaction, ZwCommitRegistryTransaction, and ZwRollbackRegistryTransaction, so multi-key updates are atomic and a crash mid-update won't leave torn state.

Protection

The store is actively defended, and not by a registry ACL. The driver sets no security descriptor of its own — no ZwSetSecurityObject, RtlCreateSecurityDescriptor, or SeAccessCheck imports, only the query forms serving object properties confirmed. A static read suggests the keys inherit ordinary service-key permissions. That inference is wrong: published testing shows access denied even to a SYSTEM prompt running as a WinTcb protected process (see credits). The mechanism is the driver's own registry callback — WESP registers CmRegisterCallbackEx and holds exactly the wildcard pattern above, which explains both the denial and why that pattern exists inferred.

So the store is not a soft enumeration target, and deleting a competitor's rule keys means defeating a kernel callback rather than editing a registry value — a meaningfully higher bar than the supported API achieves for free (§13). It does remain kernel-reachable parser input in principle, since the driver reads these binary values back through typed schemas; Rust's memory safety makes that second-order.

The lesson generalizes past this component: absence of security-descriptor APIs in an import table is not evidence that an object is unprotected, because a driver that already owns a callback surface can enforce access there instead.

11

What this means for vendors

If you adopt WESP, you take on building and maintaining a rule compiler: your detection policy becomes a filter tree, then capability-checked API calls, then a wire format. This isn't speculative. The evidence sits in Microsoft's own client code.

  • The public FilterType enum and the internal Rust discriminant are separate numbering schemes bridged by a remap table. A third scheme, _ESP_PROPERTY_QUERY_TYPE, numbers the same objects differently again. Microsoft needed translation seams between its own layers, so you'll need one between your policy language and this ABI.
  • Compiling a rule resolves typed bindings per referenced object kind, not just tree shape. That's real work, not a formality.
  • Capability negotiation makes static code generation insufficient. Properties and event capabilities are versioned per build, so your translator needs runtime probing and a fallback strategy: drop a clause, widen a filter, or fall back to client-side filtering on a broader subscription.
  • Flow control is your responsibility. You choose MaxCapacityBytes and the watermark thresholds, and you lose events if you ignore the warnings.

Treat the translation layer as a first-class component with its own test matrix across Windows builds. It's the same category of investment as maintaining ETW manifest compatibility or WFP filter-condition mappings, not a thin shim.

Before you plan around WESP, read §12. It covers the capabilities this platform doesn't replace, several of which decide whether you can retire a driver or only shrink one.

12

What you still need a driver for

WESP covers file, process, thread, registry, and handle telemetry well. It doesn't cover everything a security product does, and several of the gaps are structural rather than unfinished features.

The distinction that decides your architecture: WESP is a telemetry, policy-matching, and enforcement platform, but not a response platform. The driver can deny an operation. What no part of the API does is act after the fact. Everything below is checked against the export list, the import table, and the event catalog rather than assumed.

Response and remediation

This is the largest gap, and the easiest to overlook because it isn't a missing feature so much as a missing category. Detection is only half of what an EDR product does. The other half is acting on what it finds.

No exported function performs an action confirmed. Across roughly 120 exports, every one registers, connects, queries, describes, filters, or configures. None terminate, suspend, quarantine, or modify anything outside WESP's own object model. The driver's imports agree: there's no ZwTerminateProcess, no process or thread suspension, and no file deletion. PsTerminateSystemThread manages the driver's own worker threads, and the ZwDeleteKey and ZwDeleteValueKey imports serve its persistence store.

A user-mode agent can still perform some of these with ordinary Win32 APIs. The difference is that it does so without kernel assistance, after the fact, racing whatever it's trying to stop, and subject to the target's own defenses. That's a meaningfully weaker position than a driver acting at the callback.

Enforcement at the callback

This is the item whose status changed most under investigation, and it changed twice. The driver enforces, clients drive it, and nothing gates which action they pick — the mechanism, the callback inventory, and the disassembly are in §4. Enforcement spans file, section, volume, pipe, mailslot, KTM, eleven registry operations, and handle creation and duplication.

The client-facing shape is confirmed by a public proof-of-concept (see credits), whose rule descriptor ends with exactly the two fields this analysis predicted:

struct RuleDescriptor {
    GUID          id;
    uint64_t      order_group;   // default 100
    uint32_t      lifetime;
    /* ... reserved ... */
    uint32_t      event_type;
    const void*  event_config;
    uint32_t      modification;
    uint32_t      action;        // client-supplied ordinal
    void*         action_object; // its payload
};

The payloads match those recovered from drop_in_place<RuleAction> in §6; the proof-of-concept uses action = 1 with an event queue, the routing case. So enforcement is not the gap this section was originally written to describe, and it covers much of what a vendor minifilter and registry callback are deployed to do. Two limits still shape what it buys you:

  • Deny is not remediation. Refusing an operation is not terminating the process, quarantining what it wrote, or rolling back what it did. The response table above stays outside WESP.
  • A verdict is only as expressive as the predicate producing it. You can deny what a rule can match, which excludes anything needing memory inspection, call stacks, content, or your own code.

Where enforcement doesn't reach: image-load notifications confirmed

One callback family is structurally incapable of blocking, and it's worth stating precisely because it's the one people assume covers driver loads. ps::load_image_notify<EspCore> returns void. It calls RuleEngine::process_event<ProcessLoadImage>, and the boolean that comes back is consumed for field-cache bookkeeping. No verdict propagates, and the PLOAD_IMAGE_NOTIFY_ROUTINE contract provides nowhere for one to go. By the time it fires, the image is mapped.

WESP does capture what the callback offers. It reads IMAGE_INFO.Properties, tests ExtendedInfoPresent (bit 0x400) to pull the FileObject out of the IMAGE_INFO_EX, and stores the whole Properties dword into the event, so SystemModeImage is available to a rule. Driver loads are recognizable by a distinct tell:

lVar18 = 4;
if (param_2 != 0) { lVar18 = param_2; }   // ProcessId == 0 means kernel module
PsLookupProcessByProcessId(lVar18, ...);   // attribute the load to PID 4, System

So driver loads arrive with ProcessId == 0 and are re-attributed to the System process. WESP sees them and can match rules on them; it just can't veto at that point.

Blocking a driver load anyway. Loading a driver opens the .sys file and creates a SEC_IMAGE section for it, and both sit on the deny path in front of the image-load notification. Denying EspFsFilePreCreate or EspFsSectionPreCreate for the image stops the load outright. This is the same technique antimalware minifilters have used for years, and it's why "WESP can block driver loads" is true even though the image-load callback can't. Express the rule over file properties, not over an image-load event.

The boot handoff confirmed

A separate ELAM component covers early boot and hands off to wesp.sys through named kernel objects, all present as literals in the binary: the events \WespStarted, \WespElamStoppedCmWatch, \WespElamQueueDrained, \WespBootDoneReadingElamQueue, and the section \WespElamQueue.

A system thread signals \WespStarted, waits for \WespElamQueueDrained, maps \WespElamQueue with MmMapViewInSystemSpace, parses it into ElamNotification records with extensive bounds validation, translates each record's object IDs through a SortedMap<ElamEventObjectId, RemapEntry>, then calls RegisteredClients::find_by_id, ClientObject::open_event_queue, and queue_async_notification_internal to deliver into the client's queue. It finishes by signalling \WespBootDoneReadingElamQueue and releasing roughly 30 call sites blocked on wait_for_elam_cm_stop.

Two things follow. The ELAM component reads persisted client policy, because each notification it produces already names the client GUID that find_by_id resolves; a recorder with no policy couldn't attribute events. And \WespElamStoppedCmWatch shows it holds a registry callback during boot that hands off to wesp.sys's own, a deliberate no-gap design across the boot boundary.

This reframes the persisted store. It holds Clients, Collections, EventQueues, and Rules — everything needed to run a client's policy in the client's absence, including recreating the queue that boot events land in. Persistence isn't restart convenience; it's how the platform acts on your behalf before you exist, and it's why that store is defended by a kernel callback rather than an ACL.

What this costs you. A boot-start driver runs to completion before any consumer exists, and the event describing it arrives afterward over a lossy queue. So boot enforcement, if it happens, is someone else's code applying your policy, with no acknowledgment in the replay that your rule was evaluated or that a load was denied. Whether the ELAM component honors deny actions is not recovered: wesp.sys imports no IoRegisterBootDriverCallback and has no rule-engine instantiation for a boot event type, and the ELAM binary isn't in this sample set. For a vendor weighing whether WESP replaces a driver, this is a trust boundary moving rather than a missing feature.

Fidelity of what you do receive

Two limits shape what you can conclude from an event.

  • No content, only properties. The driver inspects content itself. It imports MmMapViewInSystemSpace, ZwQueryVirtualMemory, and MmDoesFileHaveUserWritableReferences, and feeds Defender's scan path through MpReportPostRead and MpReportPostWrite. No client API returns bytes. You can't run your own scanner, YARA rules, or unpacker on the data the event describes. Whether a content hash is among the unnamed file properties is not recovered.
  • No call stacks. The only stack-related import is IoGetStackLimits, a bounds check, with no RtlWalkFrameChain or RtlCaptureStackBackTrace confirmed. You lose caller attribution, which modern detection leans on heavily to distinguish a legitimate API use from the same call issued by injected code.

What the model does carry is better than the naming gap suggests. Process ancestry is modeled through RelatedObjectCollection::collect_process_chain, command line is available through PsProcessApi::command_line, image signature level through PsGetProcessSignatureLevel, and token privileges through a dedicated TokenPrivilegesComparison kind confirmed. For behavioral rules over process lineage and identity, the data is there.

Assurance and operational properties

  • Self-protection is expressible. Deny actions are reachable from a third-party rule, and ObHandleCreate and ObHandleDuplicate both produce verdicts, so a rule can refuse handle opens against your own processes, and file and registry rules can protect your binaries and configuration (§4). What you don't get is the rest of a driver's self-defense posture: you can't hide structures, verify your own code pages, or survive your rules being removed by someone who can reach the port (§13). Treat WESP self-protection as real but as one layer, not as a substitute for protected-process status.
  • Your agent is an ordinary process. If it's killed or crashes, observation stops. A driver keeps running and can restart its user-mode half. The persisted registration means the driver remembers you, not that it covers for you.
  • Delivery is lossy by design. Past your configured capacity, notifications are dropped. Watermark callbacks warn you first, but shedding load is your responsibility, and a gap in telemetry is a gap in detection. A driver that owns its own queue chooses its own failure mode.
  • Ordering between vendors is Microsoft's to assign. Altitude decides who sees an event first, the same way it does for minifilters, so your position in the stack is allocated rather than chosen.

The expressiveness ceiling

This is the trade underneath all the others. Your driver runs arbitrary code when an event fires. WESP gives you a fixed predicate language: boolean composition over typed properties, wildcard string matching, numeric and bitwise comparisons, and collection membership. There's no arithmetic, no regular expressions, no custom hashing, and no callback into your code.

Anything the language can't express has to be evaluated in your process after the event is delivered. That costs an IPC hop and lands after the operation has already completed. Collections soften this by letting you push an allow-list or deny-list into the kernel for in-path evaluation, which is a genuine kernel-side cache. What you can't do is compute a verdict during the event and write it back.

What you get in exchange. No kernel code to write, test, or sign. No bugcheck liability. No attestation cycle per update, no IRQL correctness to get right, and no driver to service when a callback contract changes. If your product is largely file and process telemetry with policy matching, that's a strong trade. If it blocks, responds, inspects network traffic, or reasons about call stacks, WESP in this form shrinks your driver rather than removing it, and you should plan for a hybrid.

How a WESP-based agent gets defeated

The preceding sections are organized by subsystem. This one re-indexes them by attack. Entries are deliberately terse and point back to the evidence rather than restating it.

Assume the attacker has reached Administrator or SYSTEM, the floor for touching \EspFilterPort, except where an entry says otherwise. The question is what that position buys against a WESP-based defender specifically.

Blind it: unregister the consumer

Cost: one enumerate call, one unregister call. Persists across reboot.

Client identity is a bearer GUID and no cross-client operation is caller-scoped (§10). EspEnumerateRegisteredClients publishes the GUIDs; EspUnregisterClient accepts any of them with no proof of ownership. EspRemoveAllRulesForClient is the quieter variant: leave the registration standing, strip its rules. Nothing touches the victim — no write to its process, no file modified, no service stopped — so its protected-process status is irrelevant. The agent keeps running, health checks keep passing, and it receives nothing.

Detection. Enumerate your own registration and rule set on a timer, and watch WespClientProvider for unregistration naming your GUID. Alert on the loss rather than silently re-registering: a successful unregister means something holds the privilege to repeat it.

Starve it: flood the queue

Cost: unprivileged. Persists while sustained.

Delivery is lossy past a capacity fixed at queue creation, and drops are newest-first, so a flood erases current activity while preserving the backlog (§4). Events come from ordinary file, registry and thread activity, so no privilege is needed — only a guess at what the victim's rules match, and broad subscriptions are common.

The cheapest version runs before the consumer starts. The queue is recreated from the persisted store at boot and accumulates the ELAM replay, but nothing drains it until the consumer connects. At runtime a flood races the drain rate; in that window there is no drain, so the attacker produces MaxCapacityBytes once. Any user-mode boot persistence that starts first gets this free, with no WESP://Permission claim. Note what the same window protects, though: persisted rules are live from driver init, and there's no connection handle to steal yet. The exposed assets are the undrained queue and any unsigned config read at startup.

Detection. Treat watermark transitions as security events, and check watermark state on the first EspGetNotification — a queue already at threshold on first connect is an incident, not a cold-start artifact. Since nothing counts drops, this is the only signal you get.

Evade it: stay outside the predicate language

Cost: technique selection only. Inherent.

Several categories are structurally invisible rather than unimplemented (§12): no memory-operation events, so injection and shellcode produce nothing directly; no call stacks, so injected code's API calls look legitimate; no content access, so no scanning or unpacking; no network telemetry despite the schema carrying IP and port properties. Within the language, the ceiling is itself an evasion surface — no arithmetic, regular expressions, custom hashing, or callback into vendor code — and anything a rule can't express is evaluated after the operation completed.

Detection. This is the category that decides whether you can retire a driver. Each item needs a source WESP doesn't provide: your own driver, WFP, AMSI, or the threat-intelligence ETW provider.

Outrun it: act before the client exists

Cost: boot-path persistence. Inherent to the window.

A boot-start driver runs to completion before any consumer exists, and its event arrives afterward through ELAM replay (§12). The same reasoning covers the agent's own start and any interval in which it crashed or hadn't reconnected.

Detection. Process boot events as a reconstruction pass at startup rather than assuming live coverage, and treat unexplained gaps in your own stream as adversarial until shown otherwise.

Steal it: duplicate the port handle

Cost: PROCESS_DUP_HANDLE on a consumer. Outlives the victim process.

A connection is an ordinary file object and the connection object is the credential: the tier is resolved once at connect, stored in the filter manager's cookie, and never revisited on the message path (§10). Whoever holds the handle inherits the tier computed for whoever opened it. Teardown is bound to the port, not the process — ConnectedClientProcesses::remove's only caller is reachable solely from the disconnect notification, which fires on last file-object release — so duplicating the handle and then killing the consumer leaves the connection alive in the new process confirmed.

This bypasses the admission gate rather than merely moving laterally: a caller who cannot obtain the WESP://Permission claim can still operate a fully authorized connection inferred — the mechanism is confirmed, the duplication reasoned from it, since no dynamic analysis was done. Exploitability turns on the victim's permission class:

Victim's classAntimalware PPL requiredHandle reachable by an administrator
1000000000YesNo. PPL denies PROCESS_DUP_HANDLE to unprotected callers
10000000NoYes. An ordinary process, open to ordinary handle theft

The lower class is the soft target, and it's the one a vendor would pick for a component that doesn't otherwise need PPL. Such a consumer becomes a credential store for its own platform access. (The Esp* exports take a user-mode structure rather than the raw handle, but fabricating one with the stolen handle at offset 0x10 is not a meaningful obstacle.)

Detection and mitigation. Because ObHandleCreate and ObHandleDuplicate produce verdicts (§4), a rule denying handle opens against your own consumer closes this without PPL — install it at bootstrap. PPL closes it more durably. Note the ordering dependency: that rule lives in the platform it protects, so an attacker who strips your rules first removes the defense before taking the handle. The two attacks compose. A platform-side fix would re-derive the tier at message time instead of trusting the cookie.

Impersonate it: the gate is a token claim

Cost: high.

Admission is a claims check against the primary token, not an Authenticode check on the binary (§10), so what you defend is token issuance rather than a file on disk. Placing WESP://Permission on a token needs roughly SYSTEM already, so this isn't an escalation path on its own — and it's the expensive way in. Stealing an existing connection is the cheap way, because the gate runs once per connection and the result is carried by a duplicable handle. Assume an attacker takes the cheaper path. One caveat on methodology: test-signed preview builds admit an elevated process with neither the attribute nor PPL, which is a development affordance and a reason not to generalize from test-signed experiments.

Turn it around: register and block

Cost: a registered client. Rules persist across reboot.

No capability tier gates rule actions (§4), so everything that makes WESP useful to a defender is available to whoever can register. An attacker with a registration installs blocking rules, not just subscriptions, across the full enforcement surface: file, section, volume, pipe, mailslot, KTM, eleven registry operations, and handle creation and duplication.

  • Disable a competitor without touching it. Deny handle opens against their processes, or reads of their configuration and signature files. Failures surface as ordinary kernel access denials.
  • Deny with a misleading status. STATUS_NOT_FOUND conceals rather than refuses; a file that reads as absent produces very different incident notes than one that reads as blocked.
  • Persist it. Rules survive reboot in a store defended by the driver's own registry callback, which resists a responder as readily as an attacker.

Detection. Enumerate rules, not just registrations, so you can spot rules you didn't install without waiting to notice the symptom. Treat unexplained access denials against your own components as a candidate WESP rule rather than filesystem trouble.

What is harder than it looks

  • Editing the persisted store directly. Defended by the driver's own registry callback, not an ACL; published testing shows access denied even to SYSTEM as a WinTcb protected process (§10). Note the asymmetry with the first entry: the supported API achieves a similar outcome with none of that work.
  • Assuming the absence of enforcement. Attacks that assume a WESP-based defender can only watch will fail against one that installed blocking rules (§4).
The through-line. A driver-based product's weak points are its code and its load path. A WESP-based product's are its registration, its queue, and its connection handle — none of them code the vendor wrote, none defended by the vendor's own privilege, and two of them bearer credentials where possession is authority and the platform never asks how you came by them. You stop shipping a kernel attack surface and start depending on a platform whose admission and delivery guarantees are outside your control. And because that platform enforces on behalf of whoever asks, one admission decision now governs not just who can watch the system but who can stop it.

  • not recovered Bit values for ESP_EVENT_CAPABILITIES. The ESP_EVENT_TYPE members are recovered in full and listed in §3.

  • No dynamic analysis. No live driver interaction, no traffic capture over \EspFilterPort, and no fuzzing.
Two ways to close the property ID gap. Neither needs a header. Second, enable the Microsoft.Windows.WESP.Client provider (ea3fdb23-a523-45db-bbc2-7b3bddf65666) on a build where the platform runs. Credits and corroboration

Independent public work on WESP by Jonny Johnson was used to check this analysis:

  • A First Look Inside the Windows Endpoint Security Platform — jonny-jhnson.dev/blog/a-first-look-inside-the-windows-endpoint-security-platform/
  • WespConsumerPOC, a working consumer in C++ — github.com/jonny-jhnson/WespConsumerPOC. Tested against espclient.dll 0.1.0.154553750 on ARM64, the same version analysed here on x64.

Where the two overlap, they agree. The proof-of-concept independently confirms the client registration fields including altitude, the event queue descriptor and its 64 MiB default capacity, the 0x1010-byte notification buffer, the full call sequence from EspConnectClient through arm and complete, and the property record layout of {id, type, value} triples.

It contributed several things this static analysis could not produce on its own.

  • Three real property names, kProcessCommandLine = 1, kProcessId = 6, and kProcessImagePath = 20, whose value kinds match the typed map in §6 exactly.
  • The value 1000 for process creation, which resolved the event-type numbering. It showed the 1000 group is process rather than thread, placing thread in 1–3 and shifting every subsequent group into place. An earlier draft had those groups labelled one category off.
  • The connection gate: the WESP://Permission token attribute, its two values, and the Antimalware PPL requirement on the higher one. This analysis had found the mechanism (CapabilityTier fed by token security attributes) but not the policy.
  • The port's access control and limits: default security descriptor with FLT_PORT_ALL_ACCESS restricting to Administrators and SYSTEM, and a 512-connection maximum.
  • The delivery worker: a per-queue system thread waiting on a KEVENT and delivering through FltSendMessage, which explains the KeSetEvent this analysis found in the enqueue path.
  • A disproof. Testing showed the persisted store denies access even to SYSTEM running as a WinTcb protected process. This analysis had reasoned from the absence of security-descriptor imports that the store was protected only by inherited permissions, and concluded it was a soft target for enumeration and rule deletion. That conclusion was wrong and is corrected in §10.

The blog also reports that the binaries first appeared publicly in Windows Insider Preview build 29661, and notes a CrowdStrike demonstration of blocking malware execution through this platform, which is consistent with the deny verdict table in §4.

Sources. Two binaries, wesp.sys and espclient.dll, plus a decoded TraceLogging manifest for the Microsoft.Windows.WESP.Client provider, checked against the public work listed in §16. The manifest is authoritative for field names and event structure and corroborates parameter roles derived from disassembly. It contains no enum value maps.

Method. Both binaries were analysed in Ghidra 12.1.2 with Microsoft symbol-server PDBs resolved for each. Findings come from decompiler output, import and export tables, PDB-typed signatures, string extraction from the raw images, and manual decoding of compiler-generated jump tables from raw bytes where the decompiler couldn't follow them. No dynamic tracing, driver loading, or live protocol capture took place. The main message dispatcher decompiles to more than 500,000 characters with heavily mangled types; only the passages cited in §10 should be treated as confirmed from it.
