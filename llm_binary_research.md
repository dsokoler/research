# LLMs for Vulnerability Discovery in Source, Patch Diffs, and Binaries: A Practitioner's State-of-the-Art (September 2026)

## TL;DR
- **The capability is real but narrow and evidence-graded.** LLM-driven systems now demonstrably find and even exploit real memory-safety bugs — Google's Big Sleep found an exploitable SQLite stack buffer underflow (and later CVE-2025-6965), OSS-Fuzz-Gen's AI-generated harnesses found a ~20-year-old OpenSSL OOB (CVE-2024-9143), and Team Atlanta's Atlantis won DARPA AIxCC. But headline "detection" benchmark scores collapse under realistic evaluation (PrimeVul: a 7B model at 68% F1 on BigVul drops to ~3% F1), and virtually every credible win is heavily scaffolded, not raw model output.
- **For your profile (native C/C++, Windows kernel, RE), the strongest evidence is agentic scaffolds that pair an LLM with a ground-truth oracle** — a fuzzer/sanitizer crash, a compiled PoC that BSODs, a `whoami→SYSTEM` check — not bare classification. Anthropic's June 2026 study built 8 full lowpriv→SYSTEM chains from Windows kernel Patch-Tuesday binary diffs (Ghidra + Ghidriff) at ~$2,000/exploit; an independent researcher pair found 521 candidate driver bugs across 1,873 `.sys` files at ~$3/target (with ~60% false positives on high-confidence findings).
- **The dominant failure mode is confident hallucination without a reachable path** (the curl "AI slop" problem), and it is worst exactly where you work: whole-program/temporal reasoning, lock-state/concurrency, integer arithmetic, and logic/unsafe-API bugs. Treat any LLM finding as an unverified hypothesis until a PoC, crash, or sanitizer report confirms it — the systems that actually work all enforce this.

## Key Findings

1. **Scaffolding beats the model.** Every credible result comes from a system that gives the LLM tools (code browser, debugger, disassembler via MCP, Python sandbox) and, critically, a verification oracle. Google's Naptime→Big Sleep, the AIxCC cyber-reasoning systems, and Anthropic's exploit harnesses all converge on: hypothesis → tool-driven exploration → executable verification.

2. **Variant analysis and patch-diffing are the sweet spot.** Handing the model a known bug/patch as a starting point removes the open-ended search that current models are bad at. Big Sleep was explicitly built for variant analysis; the ghidriff+LLM pipelines and Anthropic's N-day work exploit the patch as a roadmap.

3. **Benchmarks are contaminated and mostly non-native.** BigVul/Devign/Draper carry 20–71% label error and heavy duplication; function-level framing rewards shortcut learning; and the literature skews Java/Python/web. C/C++ memory-safety, kernel, and Windows evidence is thin and mostly anecdotal — though CyberGym and ARVO now target real C/C++ sanitizer crashes.

4. **On native/kernel code, LLMs are useful assistants but poor autonomous auditors.** The CSIT Windows kernel-driver study found Claude only reliably flagged a bug when the vulnerable function was pre-identified, hallucinated constantly otherwise, and entirely failed on a logical/unsafe-API-usage bug. The at-scale driver sweep confirms the pattern: high recall of candidate memory-corruption patterns, ~60% false positives, with PoC generation and true reachability being the hard parts.

5. **Binary-RE tooling has matured into a usable MCP ecosystem** (GhidraMCP, ida-pro-mcp/re-mcp, r2ai, Binary Ninja Sidekick) plus neural decompiler-refinement (LLM4Decompile) and neural binary similarity (jTrans/CLAP), but classic BinDiff/Diaphora/ghidriff remain the workhorses for patch/variant matching.

## Details

### Cross-cutting: agentic scaffolding and architecture

The defining shift since 2024 is from "ask the model if code is vulnerable" to "give the model tools and an oracle." Google **Project Naptime** (June 2024, Sergei Glazunov & Mark Brand, Project Zero) laid out the reference design: a **Code Browser** for navigating the target, a **Python tool** for scripted input generation in a sandbox, a **Debugger** for observing program state, and a **Reporter** for tracking completion. Core principles: give the model room for extended reasoning, allow interactive environment probing, verify hypotheses via execution, and — crucially — sample many independent trajectories rather than forcing one chain. On Meta's CyberSecEval 2, Naptime lifted the "Buffer Overflow" score from 0.05 to 1.00 and "Advanced Memory Corruption" from 0.24 to 0.76 (a ~20× improvement over the original paper).

**Naptime → Big Sleep** (Project Zero + DeepMind) produced the first widely publicized real-world find: an exploitable **stack buffer underflow in SQLite** (reported Oct 2024, fixed same day, pre-release so no users affected), in `seriesBestIndex` in the generate_series extension, triggered by `SELECT * FROM generate_series(1,10,1) WHERE ROWID=1;`. The `iColumn` field can hold the sentinel `-1` for ROWID, producing `iCol = -2` and a write below the `aIdx[7]` stack buffer that corrupts a pointer dereferenced on the next loop iteration. Notable specifics: the run used **Gemini 1.5 Pro**, was seeded with a recent commit for **variant analysis**, and the bug was missed by both OSS-Fuzz and SQLite's own fuzzers because the harness didn't enable the extension. In July 2025 Big Sleep found **CVE-2025-6965** (SQLite integer overflow → OOB array read, CVSS 7.2); per Google's official blog it was "known only to threat actors and was at risk of being exploited," and Google's Kent Walker stated "we believe this is the first time an AI agent has been used to directly foil efforts to exploit a vulnerability in the wild." Big Sleep also flagged a use-after-free in Chrome's ANGLE (CVE-2025-9478) and a V8 type confusion (CVE-2025-13224), and reported several Linux kernel bugs. Google says it has found "multiple real-world vulnerabilities" since launch.

**DARPA AIxCC** (finals at DEF CON 33, Aug 8, 2025) is the most rigorous public evaluation of autonomous cyber-reasoning systems (CRSs). Seven finalists ran fully autonomously — human interaction strictly prohibited — against 63 C and Java challenge projects under caps of roughly $85,000 Azure compute + $50,000 LLM credits per team over ~143 hours. **Corrected DARPA aggregate figures:** systems discovered 54 unique synthetic vulnerabilities across the 63 challenges (86% of injected vulns), patched 43 (68%), and found **18 previously unknown real-world flaws (6 in C, 12 in Java), 11 of which were patched.** DARPA reported an **average cost per competition task of ~$152** and ~45-minute average remediation.
- **Team Atlanta / Atlantis (1st, $4M):** Georgia Tech, Samsung, KAIST, POSTECH. "Ensemble-first" design integrating symbolic/concolic execution, directed fuzzing, static analysis (CodeQL for sink detection and inter-procedural distance computation), and LLMs in three modes (LLM-augmented tools, LLM agents, and fine-tuned models — the only team running fine-tuned models). Its multi-language fuzzer **UniAFL** contributed 69.2% of all proof-of-vulnerability submissions. Team Atlanta's own report claims 43 vulns found and 31 correct patches including 4 0-days (this "43/70" framing predates DARPA's revised 54/63 synthetic count). Orchestration via LangGraph + LiteLLM. Design philosophy: LLM non-determinism is "creativity" harnessed by ensembling — and it works *only* because oracles (ASAN/UBSAN/MSAN, PoV re-execution) can judge correctness. Spent ~$263/scored point.
- **Trail of Bits / Buttercup (2nd, $3M):** AI-augmented fuzzer using LLMs to craft semantically nuanced test cases; now open-source. Spent $39,600 total (~$181/point).
- **Theori (3rd, $1.5M):** LLM-forward strategy; ~$151/point.
Four of seven CRSs were open-sourced by DARPA. Sanitizers and PoV re-execution are the universal oracles; patch validation re-runs the PoV.

**XBOW** (web app/API pentesting — *not* native) became the first autonomous system to reach #1 on HackerOne's US leaderboard (June 2025; 6th globally), per head of security Nico Waisman: "For the first time in bug bounty history, an autonomous penetration tester has taken the top spot in the United States." It submitted nearly 1,060 vulnerabilities (54 critical, 242 high, 524 medium, 65 low, per its own blog and reporting) and found a previously unknown Palo Alto GlobalProtect issue affecting 2,000+ hosts. Founded by Oege de Moor (GitHub Copilot). Practitioner caveats: HackerOne ranking is partly a volume game, ~45% of submissions were still unresolved at reporting time, and this is white-box web testing, not native/kernel work.

### Surface 1: Source code analysis

**Prompting strategies.** Chain-of-thought helps but is insufficient; the higher-value patterns are (a) multi-agent debate/critic — GPTLens and VulTrial's "mock-court" prosecutor/defender/judge; (b) self-consistency / best-of-N sampling across independent trajectories (Naptime's core insight); and (c) role/persona prompting. Retrieval-augmented approaches — VulInstruct (retrieving security specs from historical patches/CVEs), LLMxCPG (generating code-property-graph queries) — consistently beat bare prompting on the PrimeVul-pair split.

**Fine-tuning vs prompting.** Fine-tuned encoders (CodeBERT/CodeT5/UniXCoder) trained on PrimeVul do poorly in realistic settings; AIxCC's Team Atlanta is the notable case where fine-tuned models paid off, but only inside an ensemble with oracles. General finding: prompting a frontier model inside a good scaffold currently dominates fine-tuning a small model for open-ended discovery.

**LLM + classical program analysis (most promising for native code).**
- **IRIS** (Ziyang Li et al., arXiv 2405.17238): neuro-symbolic — an LLM infers taint source/sink/sanitizer specs, feeds CodeQL for whole-repository taint analysis, then a second LLM pass does contextual false-positive filtering. On **CWE-Bench-Java** (120 validated real-world vulns, avg 300K LoC), IRIS with GPT-4 detected 55 vs CodeQL's 27, cut false-discovery rate, and found 6 previously unknown vulns. This is Java, not C — transfer to native taint is architecturally sound but unproven.
- **The "less is more" lesson:** restricting the LLM's role improves results. IRIS (LLM only labels APIs) is robust; QLCoder (LLM synthesizes full CodeQL queries agentically) hits 53.4% on CWE-Bench-Java but degraded when given unrestricted compile-and-run because the model overused it.
- Related lineage: LLMDFA, LLift, E&V, MoCQ (LLM-generated vulnerability patterns / DSL queries).

**LLM-assisted fuzzing (strongest native-code evidence).**
- **OSS-Fuzz-Gen** (google/oss-fuzz-gen): LLMs generate/repair fuzz harnesses. Google reported 26 new vulns including **CVE-2024-9143**, a ~20-year-old OOB read/write in OpenSSL that human-written harnesses never reached; coverage improved across 272 C/C++ projects (+370,000 lines). The repo notes 30+ new bugs from auto-generated targets unreachable by prior harnesses.
- **Fuzz4All** (universal fuzzing, ICSE 2024), ChatAFL (protocol fuzzing), TitanFuzz/CodaMosa (Python) round out harness/seed/grammar generation. The consistent theme: LLMs are good at the *harness-authoring and structured-input* bottleneck, and the fuzzer + sanitizer provides ground truth.

**Context/scaling for large codebases.** Call-graph slicing and inter-procedural context assembly, code-property-graphs feeding LLM context (AEGIS, LLMxCPG), hierarchical summarization, and — increasingly preferred — **agentic navigation** (let the agent pull only what it needs) rather than stuffing context. Long-context degradation is real: the CSIT kernel study saw large drivers "overload the context," causing hallucination and rate-limiting.

**False-positive suppression / triage.** The reliable pattern is requiring an oracle: a working PoC, a sanitizer crash, or a self-consistency vote. Validator/verifier agents and stack-trace-based PoV deduplication (Atlantis) are standard. Without an oracle, LLMs "always report a vulnerability regardless of validity."

### Surface 2: Patch-diff analysis (n-day / patch gapping)

**Source patch-diffing.** Big Sleep's variant-analysis framing (seed with a fixed commit, hunt siblings) is the template. Incomplete/insufficient-patch detection is emerging: CyberGym reported its agents surfaced 18 historically incomplete patches alongside 34 zero-days during reproduction.

**Binary patch-diffing (directly relevant to your Patch-Tuesday workflow).**
- **Tooling:** BinDiff, Diaphora, and **ghidriff** (clearbluejar, Ghidra-based) are the diffing cores; **Winbindex** locates pre/post-patch Windows binaries. LLMs sit on top for triage and semantic explanation.
- **Practitioner pipelines:** SySS's automated ghidriff+LLM patch-diff triage; **originsec/patchwatch** (open source) — ingests MSRC Security Update Guide CVEs, LLM-triages which binaries likely contain the fix (ranked with confidence scores), pulls pre/post from Winbindex, runs ghidriff in Docker, then two LLM passes (synthesis of interesting changed functions + deep decompiled-C analysis). NYU Tandon + Narf Industries published "Binary Diff Summarization using LLMs" using ghidriff as the front-end.
- **Anthropic N-day study (June 8, 2026, Frontier Red Team) — the single most important native-code datapoint.** The model was given only what an attacker has on patch day: vulnerable+patched binaries, public PDB symbols, a Ghidra decompilation, a Ghidriff function-level diff, and the MSRC advisory. On **21 Windows kernel local-EoP CVEs (Jan–Feb 2026)**, run against a live Windows Server 2025 VM with a low-priv shell and a `whoami` escalation oracle: the strongest model produced BSOD PoCs for 18/21 (~$2,200 total) and **8 distinct full lowpriv→SYSTEM exploit chains** at ~$15,700 (~$2,000/exploit). On 18 Firefox/SpiderMonkey N-days it built 8 working code-execution exploits, first exploit within an hour of the patch. Its public models (safeguards off) also built exploits, though fewer. Read this as: exploit *development* from a patch diff is no longer the scarce-expertise bottleneck it was (WannaCry took 59 days post-MS17-010; the Citrix Bleed public exploit ~2 weeks). This is Anthropic reporting on its own models — directionally credible given the mechanical `whoami` oracle, but self-published and not independently replicated.

**The "one-day exploit" literature — read critically.** Fang, Bindu, Gupta & Kang, *"LLM Agents can Autonomously Exploit One-day Vulnerabilities"* (arXiv 2404.08144): GPT-4 with a ReAct agent and the CVE description exploited 87% of a **15-vuln** benchmark; without the CVE description, only 7%. Caveats you should weigh: (a) tiny N=15; (b) all **web/container/Python-package** targets, zero native/kernel; (c) 87% is *with* the CVE text handed in — the hard part (finding/localizing) was removed; (d) the same lab's larger, cleaner **CVE-Bench** (40 web vulns, with US AI Safety Institute input) shows generic agents at ~2.5% and tool-equipped agent *teams* at ~13% in the one-day setting — far below 87%. The follow-on "zero-day team" paper (HPTSA) is likewise web-only. Bottom line: the 87% figure does not transfer to your domain.

### Surface 3: Binary analysis

**LLM + decompiler integration (MCP ecosystem you can run today).**
- **Ghidra:** GhidraMCP (LaurieWired, 7k+ stars, most popular), plus GhidrAssist, GhidrOllama, reverse-engineering-assistant, DAILA.
- **IDA Pro:** ida-pro-mcp (mrexodia; used in Cisco Talos's RE-sidekick research), now evolving into **re-mcp** with a Ghidra backend and a shared tool interface (progressive tool discovery to avoid loading ~195 schemas at once, supervisor/worker for multiple binaries, meta-tools for multi-step scripts); Gepetto (JusticeRage); aiDAPal; several other IDA MCP servers.
- **Binary Ninja:** Sidekick (commercial) + open plugins; **radare2:** r2ai.
- Cisco Talos's evaluation (an IcedID sample) and the REcon 2026 "Building Agentic RE" training reflect the emerging methodology: cloud models (Claude) are markedly better at tool-calling than local models (Devstral/Qwen/Llama via Ollama), but local keeps sensitive/malware samples private. Hard-won universal tips: **never let the LLM do base conversion or integer/byte math** — force it through a `convert_number`/`int_convert` tool (models are terrible at it); resolve library code with Lumina/FLIRT first; LLMs perform poorly on obfuscated code (deobfuscate first); steer toward disassembly over trusting decompiler output to avoid propagating decompilation errors. New attack surface to note: prompt injection *into* RE agents via crafted strings/metadata in the target binary.

**Decompiler-output improvement.** **LLM4Decompile** (Tan et al., arXiv 2403.05286, EMNLP 2024; 1.3B–33B, open weights on HF): the -End models decompile assembly directly; the **-Ref** models refine Ghidra output (the more practical mode), with the 22B-V2 outperforming 6.7B-V1.5 by ~40% and reported >100% re-executability gains over Ghidra/GPT-4o on HumanEval/ExeBench. These gains are measured in **re-executability/readability, not vulnerability-finding** — the downstream security benefit is plausible but largely unmeasured. Related: variable/type/struct recovery — DIRTY, VarBERT, **ReSym**, LmPa, SymGen; idiomatic-C recovery — Nova, SLaDe, BTC, Idioms.

**Neural binary similarity vs classic BinDiff.** jTrans (jump-aware transformer, ISSTA 2022) reported Recall@1 of 62.5% vs 32.0% for prior SOTA on the harder BinaryCorp pool, and 2× recall on real vulnerability search; CLAP (natural-language-supervised representations), PalmTree, Trex, CEBin extend this. Reality check: BinDiff/Diaphora (symbol- and CFG-driven) remain the practical default for patch/variant diffing; neural BCSD shines for cross-architecture/cross-optimization search and stripped firmware where CFG-isomorphism tools struggle.

**Windows-specific and kernel evidence.**
- **CSIT study** (Matthias Loong, "Efficacy of LLMs in detecting vulnerabilities in Windows Kernel Mode Drivers," CSIT tech blog, Nov 2025): Claude Sonnet 4.0 + IDA Pro + ida-pro-mcp. On HackSys HEVD it found the stack overflow in one prompt — but the author flagged this as confounded by the descriptive symbol name `BufferOverflowIOCTLHandler` and HEVD being in training data. On real N-days: it caught **CVE-2021-31956** (ntfs.sys integer-underflow → heap overflow in `NtfsQueryEaUserEaList`) ~100% of the time over 10+ tries **but only with the vulnerable function pre-identified via patch-diff, the bug class given, and a tuned system prompt**; it **entirely failed CVE-2023-29360** (a logical/unsafe-API-usage bug) until handed the one-line patch; on **CVE-2023-36802** (object type confusion, OOB R/W) it succeeded only when told the bug class, and hallucinated a UAF along the way. Before context tuning, "Claude always reported vulnerabilities, regardless of validity" (~100% FP tendency). PoCs mostly didn't compile first try, it sometimes refused on ethics grounds, and it defaulted to generic device-access APIs that don't work. Conclusion: assistant, not replacement; a purpose-trained RE model may help. (Single-author intern project, single model, small hand-picked set — treat as directional.) The author's own literature-review baseline cites Sean Heelan's o3 result.
- **"100+ Kernel Bugs in 30 Days"** (Yaron Dinkin & Eyal Kraft, Feb 2026): agent-swarm pipeline scraping 1,873 driver binaries (1,654 drivers), full-analyzing 202 high-risk targets selected by heuristics (IOCTL dispatch complexity, device-object count, `METHOD_NEITHER` handlers). Council of agents: decompilation agent (rename/deduce/recover dynamic calls) → attack-surface agent → code-audit agent walking the recovered call graph. **521 findings across 158 binaries**; bug mix: arbitrary read 27.6%, heap overflow 21.3%, arbitrary write 17.7%, integer overflow 6.3%, stack overflow 5.0%, UAF 4.2%, type confusion 2.1% (arbitrary R/W = 45.3%). **~60% false-positive rate on critical/high-confidence findings** (mostly real bug pattern but impractical to exploit); authors estimate **>100 genuinely exploitable LPEs**. Total cost **~$600 (~$3/target, ~$4/bug)** using mixed SLMs via OpenRouter and "maximum plain-old-python." Validation via custom QEMU virtual devices + kernel-debugged VM + BSOD-dump confirmation (which caught hallucinated crashes). Manually reported 15 to 8 vendors (Lenovo, Fujitsu, IBM, Intel, AMD, Silicom, NVIDIA, Dell); as of publication only 1 was patched with a CVE (CVE-2025-65001, Fujitsu). Example: AMD `amdfendr.sys` exposes a world-writable device whose IOCTL ops touch transport-queue descriptors without size validation → heap corruption; ships on AWS EC2 AMD Windows AMIs.
- Classic non-LLM tooling still frames the surface: **IOCTLance** (symbolic execution + taint for WDM drivers), **POPKORN** (ACSAC 2022), **Driver Buddy Reloaded** (auto-decodes IOCTL codes; identifies IRP/IO_STACK_LOCATION/DEVICE_OBJECT; flags dangerous APIs like MmMapIoSpace/rdmsr/wrmsr). The **Windows IOCTL Census** (arXiv 2606.07732) and companion "LLM-assisted target selection for Windows vulnerability research" (arXiv 2606.01364) are recent corpus-scale resources.

### Efficacy data and benchmark methodology (trust this section's numbers least at face value)

**Contamination and label noise are severe.**
- **PrimeVul** (Ding et al., ICSE 2025): built to fix BigVul/Devign/DiverseVul defects via manual-quality labeling, strict dedup, and **chronological (temporal) splits**. Result: a SOTA 7B model scored **68.26% F1 on BigVul but 3.09% on PrimeVul**; GPT-3.5/GPT-4 were "akin to random" on the pair split (each vulnerable function paired with its ~80%-identical patched version). PrimeVul-pair (435 test pairs / 870 functions) is now the standard hard benchmark, introducing the VD-S metric.
- An empirical study found **20–71% of vulnerability labels inaccurate and 17–99% of samples duplicated** in common datasets. Controlled experiments show near-linear F1 gains as test data leaks into training; SWE-adjacent studies report pass rates up to 4.9× higher on leaked vs unseen samples. Synthetic suites (Juliet, OWASP Benchmark) leak the CWE in the filename, enabling shortcut learning; detection accuracy on synthetic data ran ~10.5% higher than on real-world data on average. The "Chasing Shadows: Pitfalls in LLM Security Research" survey found data leakage in 57% of papers reviewed.

**What the main benchmarks actually measure:**
- **CyberSecEval 1/2/3** (Meta): v2 added prompt-injection, vulnerability ID/exploitation, and interpreter-abuse suites. Native-relevant finding: absolute exploit-generation performance is **low** (avg exploit scores ≤0.3; GPT-4 SQL-injection ~20%, near-zero for others), and all models were prompt-injectable 26–41%. Naptime's 20× lift over the CyberSecEval2 baseline shows the scaffold, not the model, moved the numbers. v3 adds offensive-capability evaluation (autonomous ops, scaled social engineering).
- **CyberGym** (UC Berkeley, arXiv 2506.02548): **1,507 tasks from real C/C++ OSS-Fuzz vulns across 188 projects** — execution-graded (PoC must crash pre-patch under sanitizer and pass post-patch; no partial credit, no LLM judge). This is the most native-relevant large benchmark. Best config (OpenHands + Claude-Sonnet-4) reached only **17.9%**; GPT-5 with thinking jumped 7.7%→22.0%; SWE-specialized models ≤2%. Success drops to ~10% when the required PoC exceeds 100 bytes (65.7% of tasks). Its agents also found 34 zero-days and 18 incomplete patches.
- **ARVO** (Atlas of Reproducible Vulnerabilities, arXiv 2408.02153): reproducible OSS memory vulns with triggering inputs and patches — a substrate for execution-based eval. **SEC-bench** (NeurIPS 2025): PoC generation + patching from OSS-Fuzz. **SecVulEval:** statement-level C/C++ detection. **SVEN, VulnBench, VulBench, SecBench** round out the space.
- **CWE-Bench-Java:** 120 validated Java vulns (IRIS). Java, not native.
- **AIxCC scoring:** rewarded finding vulns, proving them (PoV), and correct patching, weighted by speed/accuracy — execution/oracle-graded, the gold standard for realism, but on curated OSS challenge projects with some synthetic bugs.

**False positives, cost, and the "AI slop" problem.**
- **curl** (Daniel Stenberg): shut down its HackerOne bug bounty via PR #20312 ("BUG-BOUNTY.md: we stop the bug-bounty end of Jan 2026"), accepting last submissions through Jan 31, 2026. Per Stenberg, the confirmed-vulnerability rate "for years ran north of 15 percent, then in 2025 plummeted to below 5 percent" — "not even one in twenty was real" — while AI-generated "slop" reached ~20% of 2025 submissions. In the first 21 days of 2026, 20 submissions (7 in one 16-hour window) yielded **zero** real vulns. The program ran since April 2019 and paid out over **$100,000 across 87 confirmed vulnerabilities**. Stenberg's rule — "never report a vulnerability you cannot reproduce" — is the cheapest triage filter, and he acknowledges AI used by skilled engineers does produce real finds.
- **Cost datapoints:** AIxCC ~$152/task; Anthropic ~$2,000/Windows-kernel LPE exploit; Dinkin/Kraft ~$3/driver, ~$4/bug for *candidate* findings (before the 60% FP haircut and manual PoC work). The economics favor *generating candidates* cheaply and *validating* expensively — inverting the traditional cost structure, which is exactly why slop proliferates without an oracle gate.

### Model choice and practical tricks (2025–2026 practitioner consensus)
- **Reasoning models help on hard multi-step tasks.** On CyberGym, enabling "thinking" moved GPT-5 from 7.7%→22.0%; Claude Sonnet 4/4.5 lead several agentic security benchmarks; Anthropic's Opus 4.x / "Mythos Preview" line drove the N-day results. Sean Heelan's widely cited result used **o3** to find a real Linux ksmbd kernel zero-day, **CVE-2025-37899, in 1 out of 100 runs** (on ~12,000 lines of source); on the seeded benchmark bug CVE-2025-37778, o3 scored 8/100, Claude Sonnet 3.7 3/100, and Sonnet 3.5 0/100 — i.e., single-digit-percent hit rates, run many samples and triage.
- **Best-of-N / self-consistency is essential**, not optional — it follows directly from those base rates and Naptime's multi-trajectory principle. Big Sleep, AIxCC ensembles, and the Firefox/Windows studies all run many trials and keep the best/fastest.
- **Tool-calling quality** separates usable models: Claude and other frontier cloud models are markedly better than local Ollama models at reliably driving MCP tools; local (Qwen 2.5, Devstral, ToolACE) is viable-but-worse and slower, justified mainly by privacy for malware/sensitive binaries.
- **Force tools for arithmetic and base conversion**; keep context lean via agentic navigation rather than dumping whole drivers; deobfuscate and resolve library code before invoking the model.

### Anti-patterns / known failure modes (weighted to native/kernel)
- **Hallucinated vulnerabilities and asserting a bug with no reachable path** — the dominant failure; models "always report a vulnerability" absent an oracle.
- **Logical / unsafe-API-usage bugs** (not classic memory-corruption patterns) are systematically missed — the CSIT CVE-2023-29360 failure is canonical.
- **Whole-program and temporal reasoning** (UAF/double-free across call boundaries), **lock-state/concurrency/TOCTOU**, and **integer-overflow arithmetic** are weak spots — precisely the classes that need it most.
- **Sycophantic confirmation** of the analyst's stated hypothesis; **hallucinated API semantics**; PoCs that don't compile or use wrong device-access APIs; occasional ethics-based refusals.
- **Prompt injection into RE agents** via attacker-controlled strings/metadata in the target binary.

### Defensive / detection-engineering angle
Big Sleep is explicitly framed as *defensive* ("find bugs before release; asymmetric advantage for defenders"), and DARPA open-sourced four AIxCC CRSs for defenders. The same patch-diff→root-cause pipelines (ghidriff+LLM, patchwatch) directly support **detection-signature generation**: once the LLM produces a root cause and PoC for an n-day, the trigger conditions map onto Yara/Sigma/ETW-based detection logic. This is an active practitioner direction (e.g., REcon 2026 agentic-RE training pairs Semgrep + CodeQL MCP servers with RE workflows), though published, rigorously evaluated "LLM auto-generates the Sigma rule" results remain thin.

## Recommendations

**Stage 1 — Adopt now (high value, low risk):**
1. **Stand up an LLM-assisted binary-RE loop** with ida-pro-mcp/re-mcp or GhidraMCP + Claude (cloud for capability; local Qwen/Devstral for sensitive samples). Use it for function renaming, struct/type recovery, and decompiled-C explanation — the well-evidenced wins. Enforce the tool-for-arithmetic rule and resolve library code with FLIRT/Lumina first.
2. **Build a Patch-Tuesday patch-diff triage pipeline**: Winbindex → ghidriff → LLM synthesis/deep-analysis pass. Fork **originsec/patchwatch** as a starting point. This is where variant-analysis framing and your Windows expertise compound the model's strengths.
3. **Gate everything on an oracle.** Never action an LLM finding without a reproducing PoC, sanitizer crash, or (for kernel) a BSOD/`whoami` check. Adopt Stenberg's "no repro, no report" rule internally.

**Stage 2 — Pilot (medium effort):**
4. **Run an agent-swarm driver sweep** à la Dinkin/Kraft against your target `.sys` corpus: heuristic target selection (IOCTL complexity, `METHOD_NEITHER`, device-object count via Driver Buddy Reloaded-style triage) → decompile/attack-surface/audit agents → **QEMU virtual-device + kernel-debug VM validation**. Budget for ~60% FP on high-confidence findings; the value is cheap candidate generation, not autonomous confirmation.
5. **Pair an LLM with CodeQL/IOCTLance** (IRIS-style: LLM infers taint specs; the symbolic/static engine does the whole-program reasoning the model can't). Restrict the LLM's role — the "less is more" finding is robust.
6. **Use best-of-N aggressively** (expect single-digit-% per-sample hit rates) and log cost/bug to decide where automation pays.

**Stage 3 — Watch / re-evaluate:**
7. Track the AIxCC open-sourced CRSs (Buttercup and the four DARPA released) and the CyberGym leaderboard as capability barometers for native C/C++.
8. Track purpose-trained RE/decompilation models (LLM4Decompile successors, Nova, ReSym) for when decompiler-refinement measurably improves *downstream bug-finding* (currently unproven).

**Thresholds that change the plan:** If a frontier model crosses ~40–50% on CyberGym Level-0 (open-ended, source-only, native), or an independent (non-vendor) study replicates Anthropic's Windows-kernel exploit-chain results, shift from "candidate generation + human validation" toward semi-autonomous discovery. If your internal FP rate on LLM findings stays >50% after oracle gating, the model/scaffold is net-negative — invest in better verification, not more sampling.

## Caveats
- **Vendor self-reporting dominates the most impressive native-code claims.** Big Sleep (Google) and the N-day exploit-chain study (Anthropic) are self-published on their own models; both are directionally credible because of mechanical oracles, but neither is independently replicated. Weight accordingly.
- **The efficacy gap between benchmarks and reality is large and one-directional** (benchmarks overstate). Any F1/accuracy number from a function-level classification benchmark should be assumed inflated by contamination and shortcut learning unless it uses temporal splits and execution grading (PrimeVul-pair, CyberGym, ARVO, AIxCC).
- **The native/kernel evidence base is thin and anecdotal.** The two most relevant Windows-kernel studies (CSIT, Dinkin/Kraft) are single-team, non-peer-reviewed posts with small or heuristically-selected samples. Their qualitative conclusions are consistent and plausible; their specific numbers are not robust benchmarks.
- **"Exploit one-day at 87%" does not mean what the headline implies** for your work: web-only, N=15, CVE description supplied. The comparable cleaner benchmark (CVE-Bench) shows ~2–13%.
- **AIxCC counts were revised:** DARPA's corrected final figures are 54 synthetic vulns discovered across 63 challenges (43 patched) plus 18 real-world vulns (11 patched); some team reports use the earlier "70 vulns / 43 found" framing.
- **Fast-moving field:** model versions, MCP tooling, and benchmarks turn over in months. Repo maturity varies — GhidraMCP/ida-pro-mcp are active and widely used; many academic artifacts are research-grade.
- **Genuinely unproven where flagged:** decompiler-refinement → downstream bug-finding benefit; LLM auto-generation of detection rules; and transfer of Java taint results (IRIS) to native C.
